
# Redis 并发竞争（多客户端同时写同一 Key）

## 一、问题定义
多个客户端并发读写同一个 Redis Key，数据更新时序错乱，旧值覆盖新值，引发数据错乱。

## 二、两种主流解决方案
1. 方案 1：基于时间戳的 CAS 乐观锁（推荐，无锁阻塞）
DB 写入数据时，同步记录更新时间戳；
读取缓存时同时取出缓存内的时间戳；
执行更新前做校验：本地新数据时间戳 > 缓存内时间戳，才允许覆盖写入；
旧数据直接丢弃，避免旧值覆盖新值，无需加锁，并发性能高。

2. 方案 2：分布式悲观锁（Zookeeper/Redis 分布式锁）
操作 Key 前先抢占全局分布式锁；
同一时刻仅一个客户端持有锁，执行读写；
其余客户端阻塞等待，保证串行执行，不会出现覆盖问题；
缺点：有锁竞争、阻塞开销，高并发场景性能损耗更大。

## 三、面试口述话术
Redis 并发竞争是多客户端同时修改同一个 key，旧数据覆盖新数据的问题，两种解决思路：
乐观 CAS 方案：数据库每条数据携带更新时间戳，更新缓存前对比时间戳，只有本地数据更新时间更新才写入，不占用锁，并发性能更好；
分布式悲观锁：使用 Zookeeper 或 Redis 分布式锁，同一时间仅一个线程操作目标 key，串行执行杜绝覆盖，但会带来阻塞等待的性能损耗。
