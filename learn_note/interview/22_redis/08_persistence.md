
# Redis RDB & AOF 持久化

## 一、持久化作用
Redis 纯内存运行，宕机数据全丢；持久化将数据落盘，用于故障恢复，避免缓存雪崩。
两种持久化：RDB 快照、AOF 命令日志，生产推荐同时开启。

## 二、RDB快照持久化
原理
周期性 fork 子进程，全量生成二进制快照文件，保存某一时刻完整数据集。
优点
文件紧凑体积小，适合异地冷备份；
恢复速度远快于 AOF；
子进程 IO，主线程几乎无阻塞，高性能。
缺点
有数据丢失窗口：两次快照间宕机，丢失区间全部数据；
大数据量 fork 会短暂阻塞主线程；
只能完整快照，无法增量保存。

## 三、AOF追加日志持久化
原理
每条写命令追加写入日志，重启回放命令恢复数据；提供 3 种刷盘策略：
always：每条写入立即 fsync，零丢失，性能极差；
everysec（默认）：后台线程每秒刷盘，最多丢 1 秒数据，均衡方案；
no：交由操作系统自行刷盘，丢失不可控。
AOF 重写 rewrite
日志持续膨胀，后台生成精简新日志，合并多条操作，不影响主线程写入。
优点
丢失数据极少（everysec最多丢1s）；
追加写入，不易损坏；误删可手动删除日志指令恢复数据。
缺点
同等数据，文件体积远大于 RDB；
恢复速度慢；刷盘带来少量性能损耗；
机制复杂，早期存在恢复 bug。

## 四、生产选型建议
仅 RDB：丢失数据多，不单独使用；
仅 AOF：恢复慢，缺少可靠冷备兜底；
最佳方案：RDB + AOF 双开
AOF 作为重启优先恢复文件，保障少量丢失；
RDB 定期快照，用于异地冷备、AOF损坏时兜底快速恢复。
重启加载规则：同时开启时优先使用 AOF 恢复。

## 五、面试口述话术
Redis 提供 RDB 快照、AOF 命令日志两种持久化：
RDB 周期性生成完整二进制快照，文件小、恢复快，适合冷备，但两次快照间宕机会丢失大量数据；
AOF 追加每条写操作，默认每秒刷盘，最多丢失 1 秒数据，可手动修复误操作，但文件更大、恢复慢；
线上标准方案同时开启两者：AOF 保证少丢数据，RDB 做定期冷备份，AOF 文件损坏时可通过 RDB 快速恢复。
