
# 缓存与数据库双写一致性

## 一、主流读写方案：Cache Aside（旁路缓存）
1. 读流程
   先查 Redis，命中直接返回；未命中查询 DB，写入缓存再返回。
2. 更新标准流程：先更新 DB，再删除缓存
   不选择更新缓存的核心原因：
   缓存数据可能由多表聚合计算而来，频繁更新成本极高；
   冷数据频繁修改却极少读取，频繁更新完全浪费性能；
   懒加载思想：只有查询时才重新生成缓存，减少无效写。

## 二、两类不一致问题与解决方案
1. 场景 1：更新 DB 成功，删除缓存失败（旧缓存残留）
   方案 1：先删缓存，再更新 DB
   缺陷：更新 DB 失败时缓存为空，读取会加载旧数据到缓存，短暂不一致。
   方案 2：延时双删（生产主流）
   先更新数据库；
   立刻删除缓存；
   延迟几秒（如 5s）二次删除缓存；
   作用：覆盖更新期间并发读写入的旧缓存，消除脏数据；
   延迟删除可通过 DelayQueue、消息队列实现。
   
2. 场景 2：先删缓存、DB 未更新完成，并发读塞入旧数据
   时序：删缓存 → 读请求查旧 DB 写入缓存 → DB 更新完成，永久不一致。
   高并发强一致解决方案：读写串行队列隔离
   同一业务 key 的读写请求 hash 路由到同一内存队列；
   单线程串行执行队列任务，读写不会交叉错乱；
   优化：队列合并重复更新请求，减少重复操作；
   配套约束：多实例部署时，nginx / 网关按 key 哈希路由到同一机器，保证队列全局串行。
   串行方案弊端
   会降低系统吞吐量，机器成本上升；适合强一致低并发场景，普通业务优先延时双删。

## 三、串行队列方案生产注意点
   读请求设置超时，避免大量请求阻塞堆积；
   写 QPS 过高时扩容服务实例，分摊队列压力；
   热点 key 会造成单队列过载，需做业务拆分；
   消息/队列持久化，防止进程丢失待删任务。

## 四、面试标准口述话术
   缓存数据库一致性主流使用 Cache Aside模式，更新采用先更库再删缓存：
   不更新缓存而是删除，避免多表聚合缓存频繁无效刷新；
   基础问题：删缓存失败，用延时双删，二次清除脏缓存；
   高并发极端时序问题：删库未更新完，读请求回填旧数据；强一致场景将同key读写路由到同一内存队列串行执行，杜绝交叉脏写；
   串行方案牺牲吞吐量，绝大多数互联网业务只需延时双删即可满足最终一致性。
