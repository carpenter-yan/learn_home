
# Redis Cluster 集群原理

## 一、适用场景
海量数据、高读写并发、需要自动分片 + 内置高可用；
哨兵仅单主无法扩容写，Cluster 多主分片可水平扩展读写。

## 二、基础架构
多 Master + 多 Slave，每个主节点挂载副本；
每个节点开放两个端口：业务端口 (6379) + 集群通信端口 (16379，端口 + 10000)；
节点间通过 Gossip 协议同步集群元数据、故障信息。

## 三、Gossip 通信机制
对比集中式 (Zookeeper)
集中式：元数据统一存 ZK，实时更新，但单点压力大；
Gossip：每个节点保存完整集群元数据，节点间定期交换信息，压力分散，存在数据延迟。
核心消息类型
meet：新节点加入集群；
ping/pong：定时交换节点、槽位、故障信息；
fail：广播主节点客观宕机。
通信规则
每秒随机挑选节点发送 ping，携带部分集群元数据，同步分片与故障状态。

## 四、三种分布式分片算法对比
1. 普通 hash 取模
   hash (key) % 机器数；
   扩容 / 缩容节点数变化，几乎全部 key 路由失效，大量缓存雪崩。
2. 一致性 hash
   哈希环存储节点，增减节点仅影响局部数据；
   节点少时数据倾斜，引入虚拟节点均衡负载。
3. Redis Cluster Hash Slot（原生分片）
   固定 16384 个哈希槽；
   寻址公式：CRC16(key) % 16384；
   所有槽均匀分配给各 Master；
   扩容只需迁移少量槽位，数据影响极小；
   HashTag：大括号内字符参与 CRC 计算，实现同 key 落在同一槽，支持事务、多 key 批量操作。

## 五、故障检测与自动主从切换
1. 宕机判定
   pfail（主观宕机）：单个节点超时未收到 pong，单方面标记故障；
   fail（客观宕机）：超过半数 Master 判定 pfail，确认节点宕机。
2. Slave 选举规则
   断开主节点过久的从节点直接淘汰；
   复制 offset 越大（数据越完整），选举时间越靠前，优先投票；
   需过半 Master 投票通过，该 Slave 升级为新 Master；
   旧主恢复后自动变为新主的从节点。
3. 和 Sentinel 对比
   Cluster 内置分片 + 主从故障转移；哨兵仅单主架构，无法扩容写。两者故障判定、选举逻辑高度相似。

## 六、面试口述话术
   Redis Cluster用于海量数据高并发场景，集成分片与内置高可用：
   采用16384固定哈希槽分片，CRC16取模寻址，扩容仅迁移少量槽，支持HashTag绑定多key到同一分片；
   节点间Gossip协议同步集群元数据，相比ZK集中式压力分散，但元数据同步存在延迟；
   故障分主观pfail、客观fail，过半主节点确认宕机后，按复制偏移量选举最优从升主；
   区别于哨兵：哨兵只有单一主节点不能扩容写，Cluster多主分片可水平扩展读写，原生自带副本容灾。
