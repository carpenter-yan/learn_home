# 如何保证消息队列的高可用

## 一、面试核心思路
MQ会引入系统可用性风险，面试官考察是否掌握生产级容灾方案，分通用思路+RabbitMQ、Kafka两大主流中间件分开阐述。

## 二、RabbitMQ 高可用方案
1. 单机模式
   仅本地测试使用，无集群、无容灾，生产禁止。
2. 普通集群模式
   机制：多节点集群，队列仅存在单一节点，各节点仅同步队列元数据；
   缺陷：队列所在节点宕机则无法读写，仅提升吞吐量，不具备高可用。
3. 镜像集群模式（废弃，RabbitMQ 4.0 + 不再支持）
   机制：队列元数据 + 全量消息同步至所有节点，单节点宕机可切换其他节点消费；
   缺点：同步带宽消耗大、无法线性扩容队列，官方不再推荐。
4. Quorum Queues 仲裁队列（生产推荐，3.8+）
   基于 Raft 共识算法替代镜像模式，核心特性：
   写入需多数节点同步成功才返回 ack，数据一致性强；
   Leader 宕机自动重新选举，故障转移无需人工干预；
   支持段式存储，持久化性能优化，可独立扩容副本；
   限制：仅支持持久化消息，至少 3 个节点才能形成有效仲裁；

## 三、Kafka 高可用机制（原生分布式架构）
1. 基础架构
   多 broker 集群，Topic 拆分为多个 Partition，分散存储在不同节点，天然分布式。
2. 0.8 版本前：无高可用
   Broker 宕机，其上所有 Partition 数据不可读写，无副本容错。
3. 0.8 版本后：副本 Replica 机制（核心 HA）
   每个 Partition 配置多个副本，分布在不同机器；
   副本区分 Leader（读写唯一入口）、Follower（同步数据）；
   流程：生产者写入 Leader，Leader 落盘后 Follower 主动拉取同步；
   故障容错：若 Leader 所在 Broker 宕机，从存活 Follower 自动选举新 Leader，业务正常读写；
   同步策略可配置：等待全部 / 部分 Follower 同步完成再返回写入成功。
   关键区别 RabbitMQ vs Kafka
   RabbitMQ 传统中间件：单队列完整数据存储在单节点，镜像全量复制，扩展性差；仲裁队列基于 Raft 优化；
   Kafka 分布式 MQ：Topic 分片分散多节点，分区副本机制，天然支持水平扩容。
## 四、面试标准答题话术（简洁精炼）
   MQ会引入可用性风险，高可用主要依靠集群副本机制实现，我分RabbitMQ和Kafka分别说明：
   - RabbitMQ：单机无容灾，普通集群仅扩容吞吐无高可用；旧镜像集群同步开销大已废弃，生产推荐仲裁队列，基于Raft算法，多数节点确认才算写入成功，Leader故障自动重选，需至少3节点部署；
   - Kafka：原生分布式，Topic拆分多分区分散存储，依靠分区副本实现HA，分区分Leader与Follower，读写只走Leader；Leader宕机自动从存活副本选举新Leader，同步ack策略可灵活配置保障可靠性；
   - 两者核心差异：RabbitMQ队列数据集中存储，靠Raft仲裁队列提升容错；Kafka分区分片分散多节点，天然支持水平扩容。
