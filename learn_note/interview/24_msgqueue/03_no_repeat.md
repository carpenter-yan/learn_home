# 如何保证消息不被重复消费？

## 一、核心结论
RabbitMQ/Kafka/RocketMQ都无法彻底杜绝消息重复，重复消费属于正常现象，中间件不负责去重，必须业务层实现消费幂等。
幂等定义：同一条消息多次消费，最终业务数据结果不变，不会产生脏数据。
## 二、重复消费产生原因（以 Kafka 举例）
- offset 提交机制缺陷
Kafka 每条消息分配唯一 offset，消费者定时提交 offset 记录消费点位；新版 offset 存储在内部主题__consumer_offsets，不再依赖 Zookeeper。
- 典型重复场景：
消息业务逻辑处理完成，但 offset 还未提交，进程被 kill、宕机、网络超时；重启后从旧 offset 重新拉取消息，造成重复消费。
- 其他诱因：生产者重试发送、Broker 故障转移、集群网络抖动。
举例
offset=152、153、154 三条消息，消费完 153，未提交 offset 就宕机；重启后从 152 重新消费，152、153 重复执行，直接导致数据库重复插入。

## 三、4 套生产幂等落地方案
1. 数据库唯一索引（推荐，写库场景）
   每条消息携带业务唯一 ID（订单号、流水号），数据表对该 ID 建立唯一约束；重复插入数据库直接抛冲突异常，拦截脏数据。
2. 前置业务查询判断
   消费前根据唯一 ID 查询数据库：
   无记录：执行业务逻辑；
   已存在：直接丢弃消息，不重复处理。
3. Redis全局ID去重（高并发场景）
   生产者每条消息携带全局唯一 msgid；
   消费逻辑：
   1）查询 Redis 是否存在该 msgid；
   2）不存在则执行业务，完成后写入 Redis；
   3）存在直接跳过消费；
   可设置 key 过期时间，控制缓存存储压力。
4. 天然幂等操作（无需额外处理）
   Redis set/put 覆盖操作，重复执行无副作用；
   数据库 update 更新语句（基于唯一 ID 更新，重复执行数据不变）。
## 四、标准面试口述答题话术
   所有MQ都无法从中间件层面彻底杜绝重复消费，核心解决方案是业务层保证消费幂等。
   重复消费根源：以Kafka为例，消费者处理完消息但offset未提交，服务宕机重启后重新拉取消息；网络重试、集群切换也会触发重复。
   幂等含义：一条消息多次消费，业务数据保持一致，不会重复新增、重复扣款。
   四种落地实现：
   ① 数据库唯一索引，靠数据库约束拦截重复插入；
   ② 消费前查询业务ID，已处理直接跳过；
   ③ Redis缓存已消费唯一ID，高并发快速去重；
   ④ 使用Redis set、数据库update这类天然幂等操作。
   实际开发根据业务并发、存储成本组合选用。
