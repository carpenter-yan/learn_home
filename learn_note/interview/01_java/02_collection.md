
## 一、 常见的集合有哪些？
### 一、集合两大根接口
1. Collection：单列集合，存单个对象
    - List：有序、可重复、有索引
    - Set：无序、不可重复
    - Queue：队列，先进先出
2. Map：双列集合，键值对 key-value，key不可重复
### 二、List 实现类
- ArrayList
底层：可变数组  特点：查询快、增删尾部快；中间插入删除慢；线程不安全  扩容：默认10，1.5倍扩容
- LinkedList
底层：双向链表 特点：首尾增删极快；随机查询慢；线程不安全 可当栈、队列、双端队列使用
- Vector 底层数组，方法加synchronized，线程安全，性能差，基本淘汰
- Stack：继承Vector，栈，过时不推荐
### 三、Set 实现类
- HashSet 底层：HashMap，元素存map的key 无序、去重；依赖hashCode()+equals()判断重复
- LinkedHashSet 底层：LinkedHashMap 有序（插入顺序）、去重；比 HashSet多维护双向链表
- TreeSet 底层：TreeMap（红黑树） 自动升序排序；元素实现Comparable或传入Comparator
### 四、Queue 队列常用
- ArrayDeque：数组双端队列，替代Stack/LinkedList 做栈，性能更好
- PriorityQueue：优先队列，底层堆，自动按优先级排序
- LinkedList：可作普通队列
### 五、Map 实现类（高频）
- HashMap（JDK8重点）
底层：数组 + 链表 + 红黑树；链表长度≥8转红黑树，≤6退回链表 无序，key 唯一；线程不安全 默认容量16，负载因子0.75，扩容2倍
- LinkedHashMap 继承HashMap，额外维护双向链表，保持插入顺序；可实现LRU缓存
- TreeMap 红黑树，key自动排序，需实现比较器
- HashTable 全方法加锁，线程安全，性能差，淘汰；不允许key/value为 null
- ConcurrentHashMap 线程安全高性能 map；JDK7分段锁、JDK8CAS+synchronized锁头节点 高并发场景首选
### 六、线程安全集合（加分）
- 旧：Vector、HashTable（低效）
- 工具包装：Collections.synchronizedList/Set/Map，全局锁，并发一般
- JUC高性能：
CopyOnWriteArrayList：写时复制，读多写少场景
ConcurrentHashMap：并发 Map 首选
BlockingQueue 阻塞队列：ArrayBlockingQueue、LinkedBlockingQueue
### 七、面试口述总结
Java集合分Collection单列、Map双列两大体系：
List：ArrayList数组查快增删慢；LinkedList链表首尾操作快；Vector 过时；
Set：HashSet无序去重、LinkedHashSet有序、TreeSet自动排序；
Map：HashMap日常最常用，JDK8优化红黑树；LinkedHashMap有序可做LRU；TreeMap排序；并发用ConcurrentHashMap；
线程安全不推荐Vector/HashTable，读多写少用CopyOnWriteArrayList，高并发Map用ConcurrentHashMap。

## 二、ArrayList和LinkedList区别？
### 一、底层结构
ArrayList 底层动态 Object 数组，连续内存空间。
LinkedList 底层双向链表，节点分散存储，每个节点存数据、前驱、后继指针。
### 二、核心性能对比
1. 查询 /get (index)
   ArrayList：随机访问O(1)，直接通过数组下标寻址，速度极快。
   LinkedList：必须从头 / 尾遍历到目标下标，平均 O (n)，查询慢。
2. 头部/中间插入、删除
   ArrayList：需要移动大量元素，数组扩容还会拷贝，O (n)，效率低。
   LinkedList：只修改节点指针，不用移动数据，O (1)，首尾增删性能优势巨大。
3. 尾部追加 add ()
   ArrayList：不触发扩容 O (1)；扩容时数组复制 O (n)。
   LinkedList：直接尾插，永远 O (1)。
### 三、内存占用
   ArrayList：仅存储元素数组，内存紧凑，开销小。
   LinkedList：每个节点多存两个指针（prev、next），内存开销更大。
### 四、扩容机制
   ArrayList：默认容量 10，满了按1.5倍扩容，新建数组复制所有元素。
   LinkedList：无扩容概念，按需创建节点，无复制开销。
### 五、线程安全
   两者都非线程安全，多线程并发读写会并发修改异常。
### 六、适用场景
   优先ArrayList 查询多、尾部新增多，很少在头部/中间频繁删插（90% 业务场景）。
   优先LinkedList 频繁在首尾做插入删除、用作队列/栈；大量随机遍历查询不推荐。
### 七、面试口述标准答案
   两者核心差异来自底层数据结构：
   ArrayList 底层是连续数组，随机查询速度 O (1)，但中间、头部增删需要移动元素，效率低；支持自动扩容；内存占用小。
   LinkedList 是双向链表，下标查找需要遍历，查询慢；仅修改指针，首尾增删效率高；每个节点带前后指针，内存开销更大，无扩容机制。
   使用建议：业务以查询为主选 ArrayList；频繁首尾插入删除、做队列栈再用 LinkedList。

## 三、HashMap底层数据结构？
1、JDK1.7 ，由“数组+链表”组成，数组是HashMap的主体，链表则是主要为了解决哈希冲突而存在的。
2、JDK1.8 ，由“数组+链表+红黑树”组成。当链表过长，则会严重影响HashMap的性能，红黑树搜索时间复杂度是O(logn)，而链表是O(n)。
因此，JDK1.8 对数据结构做了进一步的优化，引入了红黑树，链表和红黑树在达到一定条件会进行转换：
当链表超过8且数据总量超过64才会转红黑树。将链表转换成红黑树前会判断，如果当前数组的长度小于64，那么会选择先进行数组扩容，而不是转换为红黑树，以减少搜索时间。

## 四、为什么在解决hash冲突的时候，不直接用红黑树？而选择先用链表，再转红黑树?
不会一上来就用红黑树，核心是权衡内存开销、增删性能、查询性能：
节点数量少时链表更轻量：链表结构简单，插入只需追加节点，没有红黑树左旋右旋平衡的复杂运算，速度更快、占用内存更小；短链表遍历次数很少，性能差距不大。
只有链表过长（≥8），链表遍历O(n) 性能暴跌，红黑树O(logn) 的查询优势才能覆盖它的维护成本；
阈值 8 基于泊松概率，正常 hash 分布下很难出现长链表；退化阈值 6 用来缓冲，防止频繁切换结构带来性能损耗；
如果全部桶直接用红黑树，绝大多数无冲突/少量冲突的桶会白白浪费内存，整体读写性能下降。

## 五、HashMap默认负载因子是多少？为什么是 0.75，不是 0.6 或者 0.8 ？
Node[] table的初始化长度length (默认值是16)，Load factor为负载因子 (默认值是0.75)，threshold是HashMap所能容纳键值对的最大值。
threshold = length * Load factor。也就是说，在数组定义好长度之后，负载因子越大，所能容纳的键值对个数越多。 
默认的loadFactor是0.75，0.75 是对空间和时间效率的一个平衡选择，一般不要修改，除非在时间和空间比较特殊的情况下 ：

如果内存空间很多而又对时间效率要求很高，可以降低负载因子Load factor的值 。
相反，如果内存空间紧张而对时间效率要求不高，可以增加负载因子loadFactor的值，这个值可以大于1

## 六、HashMap的put方法流程？
JDK8 HashMap put 流程分为7步：
1. 通过扰动函数计算 key 哈希，key 为 null 哈希固定 0；
2. 如果哈希数组未初始化，执行 resize 初始化容量 16；
3. hash 与数组长度 - 1 做与运算定位哈希桶；
4. 若桶为空，直接新建节点放入；
5. 桶不为空先判断头节点 key 是否一致，一致直接覆盖 value；
6. 头节点是树节点就走红黑树插入；是链表则循环遍历，找到相同 key 覆盖，没找到就在尾部新增；链表长度到 8 且数组≥64 转为红黑树；
7. 新增成功后元素总数 size 自增，超过扩容阈值就执行两倍扩容，最后有旧值返回旧值，新增返回 null。

## 七、HashMap扩容方式？
HashMap扩容流程如下：
元素数量size超过阈值（容量 ×0.75）触发扩容，新数组容量扩大为原来 2 倍；
扩容resize方法同时负责初始化数组和迁移数据；
迁移时不需要重新计算key的 hash，通过hash&oldCap 判断元素新位置，只有两种情况：留在原下标、或原下标 + 旧容量；
链表拆分为高低两条链表，尾插迁移，解决JDK7并发扩容环形链表死循环 bug；
红黑树拆分后节点少于6会退化成单向链表。

## 八、HashMap为什么线程不安全？
HashMap 线程不安全分多层原因：
- 没有任何同步机制，多线程并发put会发生节点覆盖，数据丢失；
- size自增非原子操作，并发写入导致元素计数不准确；
- 迭代遍历期间其他线程修改集合，抛出并发修改异常；
- JDK7扩容头插法会形成环形链表，get时死循环占满 CPU；
- JDK8改用尾插修复了死循环，但数据覆盖、计数错乱等基础安全问题依然存在。

## 九、ConcurrentHashMap实现原理？
### 一、核心定位
线程安全的高性能哈希 Map，替代 Hashtable、Collections.synchronizedMap； 全程细分锁/CAS，不全局锁定整张数组，并发吞吐量远高于加锁包装HashMap。
### 二、JDK7 实现：分段锁 Segment
1. 结构：Segment数组 + HashEntry链表
   外层 Segment[] segments（分段锁数组，默认 16 段）
   每个 Segment继承ReentrantLock，自带独立互斥锁；
   Segment内部是HashEntry[] 哈希桶 + 单向链表。
2. 并发逻辑
   计算key hash，定位到对应 Segment；
   操作该段前，只锁住当前这一段 Segment，其他分段完全无锁可并发读写；
   多线程操作不同 Segment 完全并行，同一 Segment 互斥；
   扩容仅针对单个 Segment，不影响其他分段。
   缺点 默认最多16把锁，并发上限受分段数量限制； 链表过长查询O(n)，无红黑树优化；内存占用更高，双层数组。
### 三、JDK8 重大重构：取消分段锁，CAS + synchronized 锁头节点（主流考点）
1. 底层结构
   与 HashMap 完全一致：Node<K,V>[] table 哈希桶数组 + 单向链表 + 红黑树； 不再有 Segment，锁粒度细化到单个哈希桶头节点。
2. 核心并发手段
   CAS 无锁操作 桶为空时，使用 casTabAt 原子操作插入头节点，不加锁；多线程竞争 CAS 失败自旋重试。
   synchronized 锁住桶头 Node 桶已有元素时，对链表 / 红黑树的头节点对象加内置锁； 只锁当前哈希桶，其他桶线程可并发读写，粒度极细。
   volatile 保证可见性 table、Node 的 val、next 使用 volatile，读写内存可见，避免脏读。
3. put 核心流程
   扰动函数计算 hash；
   table 未初始化则 CAS 初始化；
   定位桶下标 i：
   桶为 null：CAS 尝试插入新 Node，失败则自旋；
   桶不为空，且该桶正在扩容（fwd 标记）：协助扩容；
   正常链表 / 树：对桶头 synchronized 加锁，遍历链表 / 红黑树：
   key 存在则覆盖 value；不存在尾部新增；链表≥8 树化；
   新增成功更新 size（CAS 计数 baseCount / 计数器数组 counterCells）；
   判断达到阈值，触发扩容，多线程可并发协助迁移数据。
4. 扩容机制优化（加分）
   扩容标记 ForwardingNode：标记当前桶正在迁移；
   多线程并发协助迁移：线程 put/get 时发现桶是 ForwardingNode，会帮忙搬运数据，加速扩容；
   迁移逻辑同 HashMap：高低位拆分链表，尾插，无环形链表。
5. size 计数
   放弃单一 volatile 变量，使用 baseCount + counterCells 分散计数：
   并发写入竞争时，分散到多个 cell 数组 CAS 累加，减少竞争，统计总数时求和。
### 四、JDK7 vs JDK8 核心区别对比

   维度|JDK7 Segment 分段锁|JDK8 CAS + synchronized 锁桶头
    --|--|--
   锁粒度|分段（16 段）|单个哈希桶，粒度更细
   数据结构|双层数组，只有链表|单层数组，链表 + 红黑树
   并发能力|最多 16 线程并行|支持数组长度级并发，上限更高
   扩容|单段独立扩容，不能协助|多线程并发协助迁移
   写入性能|一般，分段锁竞争|更高，空桶 CAS 无锁
   内存开销|双层数组占用大|结构和 HashMap 接近，更省内存

### 五、面试口述标准答案
   ConcurrentHashMap 分两个版本实现：
   JDK7使用 Segment分段锁：外层16个独立分段，每个分段一把ReentrantLock；操作只锁对应分段，不同分段并发执行；缺点是并发上限固定、只有链表查询慢。
   JDK8完全重构，取消分段锁：底层结构和 HashMap 一致，采用 CAS+synchronized 实现并发：
   桶为空时用CAS无锁插入； 桶有元素则锁住链表 / 红黑树的头节点，锁粒度细化到单个桶，并发度大幅提升； 支持多线程协助扩容，红黑树优化长链表查询；
   使用volatile保证数据可见，分散式计数器统计size，减少CAS竞争。
   整体相比Hashtable全局锁、同步Map，并发性能大幅提升，是高并发存储键值对的首选。
### 补充追问：为什么 JDK8 不用 ReentrantLock 改用 synchronized？
   JVM对synchronized 持续优化（偏向锁、轻量级锁、重量级锁），性能已追上甚至超越 ReentrantLock；
   锁对象是桶头 Node，生命周期随数组，无需额外对象；
   红黑树遍历场景下，内置锁语法更简洁，减少代码复杂度。
