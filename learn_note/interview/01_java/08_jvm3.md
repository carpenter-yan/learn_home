## 如何排查OOM问题？
OOM全称OutOfMemoryError，细分 5 大类，先分清类型，再按步骤定位，拒绝盲目加堆。
### 一、第一步：区分 OOM 具体类型（日志关键字判断根因）
根据报错日志，先归类，方向完全不同

报错关键字|原因分类|核心说明
--|--|--
Java heap space|堆 OOM|堆内存不足，对象太多无法回收
unable to create new native thread|线程栈 OOM|线程数量过多，操作系统分配不出栈内存
Metaspace / PermGen space|元空间 OOM|类、常量、注解、动态代理加载太多
Direct buffer memory|堆外内存 OOM|NIO ByteBuffer、Netty 堆外内存泄漏
GC overhead limit exceeded|GC 耗时超限|GC 占 CPU 过高，回收效率极低，JVM 自保报错

### 二、通用前置配置（排查前必须开启，否则无日志）
启动JVM添加参数，出事自动留快照：
```
-XX:+HeapDumpOnOutOfMemoryError  # OOM自动生成堆快照hprof文件
-XX:HeapDumpPath=/xxx/heap.hprof  # 指定dump保存路径
-XX:+PrintGCDetails -Xloggc:gc.log # 打印完整GC日志
-XX:+PrintGCApplicationStoppedTime # 打印STW停顿
```
生产一定要提前配置；事后OOM没dump基本很难定位。 不要只靠肉眼看代码，必须结合 dump+GC 日志。
### 三、堆 OOM（Java heap space）完整排查步骤（最常见）
步骤 1：分析GC日志，判断是「内存泄漏」还是「内存容量不够」
打开 gc.log 重点看两点：
内存泄漏：每次GC后，可用内存越来越少。老年代占用持续走高，Full GC频繁，回收完内存依旧涨，属于代码对象无法释放。
内存容量不足：GC可以回收大量内存，只是业务峰值瞬间创建对象太多，堆太小扛不住，单纯硬件资源不够。

步骤 2：解析hprof堆快照（主流工具二选一）
JDK 自带：jhat：命令行简陋，只适合简单排查，不推荐线上。
MAT（Memory Analyzer Tool）：最专业免费工具（推荐）。
IDEA 内置 Profiler、JVisualVM：适合测试环境实时监控。
MAT 核心排查流程
打开 hprof，选择 Leak Suspects Report（泄漏嫌疑报告），MAT自动给出可疑对象、线程、类排行。
看两个核心面板：
Histogram 直方图：按类统计对象数量、占用内存。定位哪个类创建了海量实例。
Dominator Tree 支配树：找出留存内存最多的对象，谁持有大量对象无法被GC，找到引用链源头。
重点查引用链：右键对象 → List objects → with incoming references，一路往上找到是谁强引用住对象。

步骤 3：高频堆泄漏常见原因
静态集合（static List/Map）长期持有对象，全局永不释放；
线程池线程常驻，ThreadLocal使用后没有remove，value一直被线程持有；
缓存无过期策略（HashMap 做本地缓存，只put不删）；
大集合未清空，循环不断add，没有限制上限；
第三方框架缓存、连接池、回调、监听器注册后未注销；
大文件一次性加载全量进内存，没有分片读取。

步骤 4：验证&修复
泄漏：改代码断掉无效强引用（清理集合、手动 remove ThreadLocal、加缓存过期淘汰）；
容量不足：优化业务减少临时对象，合理调大Xmx/Xms，优先优化代码，不要无脑加堆。

### 四、各类其他OOM专项排查
1. GC overhead limit exceeded
   触发规则：GC花费CPU时间超过98%，回收内存少于2%，JVM 直接抛OOM自保。
   根因：内存泄漏严重，GC疯狂干活却收不出内存。
   排查：和堆OOM完全一致，抓dump找泄漏；少数情况新生代太小，频繁 YGC。
2. Metaspace元空间 OOM
   元空间存放：类信息、方法、常量池、注解、动态生成类（CGLIB、JDK 代理、Groovy）。
   排查方式：
   Jvisualvm/MAT 查看类加载总数，是否持续上涨；
   常见原因：热部署频繁、动态代理疯狂生成类、重复加载 jar 包、自定义类加载器不销毁；
   优化：-XX:MaxMetaspaceSize调上限，修复重复加载类逻辑。
3. Direct buffer memory 堆外内存OOM
   NIO、Netty、OkHttp 使用堆外 DirectByteBuffer，不受 Xmx 管控。
   底层：堆外内存靠 System.gc 手动回收，Full GC 才会清理；业务频繁分配堆外、没主动释放就溢出。
   排查：
   Netty 内存泄漏检测开启：-Dio.netty.leakDetection.level=PARANOID；
   代码是否忘记调用 buffer.release ()；
   优化：主动释放堆外内存，限制堆外最大大小-XX:MaxDirectMemorySize。
4. unable to create new native thread 线程OOM
   原因：线程太多，OS 无法分配线程栈。
   排查：
   jstack 进程号导出线程栈，统计线程总数；
   定位无限创建线程的代码：无界 new Thread、线程池无 maxSize、死循环开线程；
   优化：使用有界线程池，限制最大线程；适当调小 - Xss，腾出更多内存开线程。
### 五、线上实时排查命令（不用等 OOM 复现）
1. 整体内存概览
   jstat -gc 进程号 1000 # 每秒打印GC、新生代老年代内存变化，长期观察涨跌
   jmap -heap 进程号    # 查看堆配置、各区当前占用
2. 手动生成 dump（即将 OOM 但还没崩溃）
   jmap -dump:format=b,file=heap.hprof 进程ID
3. 查线程（线程 OOM、死循环）
   jstack 进程ID > thread.txt
4. 实时观测内存、创建对象
   jvisualvm 可视化远程监控
### 六、极简排查通用流程背诵版
看报错日志，分清OOM类型；
查看GC日志，判断是泄漏还是堆太小；
拿hprof用MAT分析，直方图找大对象，支配树找引用链；
定位代码强引用源头，针对性改代码；
非堆OOM（元空间、堆外、线程）走对应专项排查；
生产提前配置自动 dump，避免出事无依据。
### 七、高频踩坑提醒
不要上来就-Xmx4g无脑加大堆，内存泄漏加多大都会OOM；
ThreadLocal必须用完 remove，是线上TOP1 泄漏点；
本地复现不了线上OOM，90%是并发场景下的对象堆积，必须靠线上dump；
堆外内存不受Xmx限制，只改堆参数没用。

## 类加载机制是什么？
### 一、整体总览
JVM把.class字节码文件加载进内存，校验、处理，最终生成可在堆使用的Class对象，这个全过程就是类加载机制。
分为5个大阶段：加载、验证、准备、解析、初始化；使用和卸载不属于加载阶段。
类加载不是必须程序启动一次性全加载，Java是延迟懒加载，用到类才加载。
### 二、类加载完整五大阶段
1. 加载（Loading）
   通过类的全限定名（包名 + 类名）获取二进制字节流；来源可以是本地文件、jar包、网络、动态生成（CGLIB）、数据库。
   将字节码代表的静态存储结构，转为方法区（元空间 Metaspace）运行时数据。
   在Java堆生成代表这个类的java.lang.Class对象，作为方法区类数据的访问入口。
2. 验证（Verification）
   保证class字节码合法、安全，不会危害 JVM。
   四层校验：
   文件格式校验：class文件魔数、版本号，确保是合法字节码，不是乱码。
   元数据校验：语法、继承合理性（比如final类不能被继承）。
   字节码校验：指令合法，不会做栈溢出、跳转非法、类型错乱等危险操作。
   符号引用校验：引用的类、方法、字段是否存在可访问。
3. 准备（Preparation）
   为类静态变量（static）分配内存，赋初始默认零值。
   基本规则：
   int → 0，boolean→false，引用→null；
   普通成员变量不在这里分配，创建对象时才分配；
   static final编译期常量，直接赋值字面量，不走零值。
```
   public static int num = 100;
   // 准备阶段：num=0；初始化阶段才赋值100
   public static final int A = 99;
   // final常量准备阶段直接赋值99
```
4. 解析（Resolution）
   把常量池里的符号引用，替换为内存直接可用的直接引用。
   符号引用：字符串描述（比如com.User）； 直接引用：内存地址、指针、偏移量，可以直接定位目标。
   解析四类：类/接口、字段、方法、接口方法。
5. 初始化（Initialization）
   真正执行Java 代码，给static变量赋程序员写的初始值，执行静态代码块static{}。
   主动引用才触发初始化，被动引用不会初始化。
   触发类初始化的主动场景（6 种）
    - new 创建对象；
    - 读取/修改static非final变量；调用static方法；
    - 反射Class.forName()；
    - 子类初始化，父类必先初始化；
    - main方法所在主类启动；
    - JDK动态代理、自定义注解触发。
      被动引用（只加载不初始化）
    - 访问static final编译期常量，只走编译期，类不初始化；
    - 通过数组定义类：User[] arr = new User[10]，不会初始化 User；
    - 子类引用父类静态变量，只会初始化父类，子类不初始化。
### 三、类加载器分类（4 类）
- 启动类加载器 Bootstrap ClassLoader
  C++实现，无Java对象，加载jre/lib核心基础类：java.lang.*、集合、IO 等核心 JDK 类。
- 扩展类加载器 Extension ClassLoader
  Java实现，加载jre/lib/ext扩展目录下 jar。
- 应用程序类加载器 Application ClassLoader（系统类加载器）
  日常主力加载器，加载项目classpath 下自己写的代码、第三方依赖 jar。
- 自定义类加载器
  继承ClassLoader重写findClass，自定义加载逻辑：热部署、代码加密、从网络加载class。
### 四、双亲委派模型（核心重点）
1. 工作流程
   加载类时，不会自己先加载，向上委派给父加载器；逐级向上直到启动类加载器。
   AppClassLoader → 委托给 Extension；
   Extension → 委托给 Bootstrap；
   Bootstrap 能加载就加载；加载不到，原路退回，由子类加载器自己加载。
   一句话：向上委派查找，向下负责加载。
2. 双亲委派两大好处
   安全防护：防止自定义java.lang.String 这类核心类篡改。
   用户自己写一个java.lang.String，委派给Bootstrap，Bootstrap加载系统自带String，永远不会加载用户恶意类。避免核心API 被篡改。
   类全局唯一性：保证同一个类只会被加载一次，不会多份Class，避免类型混乱。
3. 打破双亲委派的场景
   正常是双亲委派，以下场景主动打破：
   SPI机制（JDBC、Dubbo）：线程上下文类加载器；父加载器看不到下游资源，反向委派。
   热部署（Spring devtools、Tomcat 热加载）：自定义加载器不停替换class。
   OSGi模块化：每个模块独立类加载器，互相隔离，完全抛弃双亲委派。
### 五、双亲委派实现源码关键逻辑（ClassLoader.loadClass）
先检查类是否已加载；
未加载，优先委派父加载器；父不为空递归父.loadClass；父是 null 委派 Bootstrap；
所有父都加载失败，调用自身findClass () 由当前加载器读取字节码；
重写findClass 可以自定义加载，保留双亲委派；重写 loadClass 彻底破坏双亲委派。
### 六、类的卸载
只有满足全部条件，类才会被元空间 GC 卸载：
Class 所有实例全部回收； Class 对象无任何强引用；
加载该类的类加载器实例被回收。
日常 AppClassLoader 不会销毁，普通业务类几乎不会卸载；热部署依靠自定义加载器销毁实现类卸载。
### 七、极简背诵版
类加载五步：加载、验证、准备、解析、初始化；准备赋零值，初始化执行静态代码。
主动引用触发初始化，被动引用只加载不初始化。
四大加载器：引导、扩展、应用、自定义。
双亲委派：向上委托找类，父优先加载；防核心类篡改，保证类唯一。
SPI、热部署、OSGi 打破双亲委派。

对象的栈上分配？
一、基础概念
正常 Java 对象全部在堆分配，GC 负责回收。
栈上分配：JVM 通过逃逸分析判定对象不会逃出当前方法、当前线程，直接把对象分配在虚拟机栈帧中，不进堆。
方法执行结束，栈帧出栈自动销毁对象，完全不需要 GC 回收，减少堆压力、降低 Minor GC 频率。
配套优化：标量替换（栈上分配的主流落地形式）。
二、逃逸分析：判断能不能栈分配
JIT 编译（JIT 即时编译）做逃逸分析，判断对象是否逃逸：
不逃逸：对象只在当前方法内使用，没有传出方法、没有给到其他线程 → 支持栈上分配 / 标量替换。
方法逃逸：对象作为返回值抛出方法、赋值给成员变量，方法外可以访问 → 必须堆分配。
线程逃逸：多线程共享这个对象，别的线程能访问 → 必须堆分配。
示例：不逃逸
java
运行
public void calc() {
User user = new User();
user.age = 10;
System.out.println(user.age);
// user全程没出方法、没有多线程共享，无逃逸
}
示例：方法逃逸
java
运行
public User calc() {
User user = new User();
return user; // 对象返回，外部可访问，逃逸，只能堆分配
}
三、标量替换（栈上分配真正实现方案）
1. 标量与聚合量
   标量：无法拆分的基础数据，int、long、boolean、引用地址；可以直接存在栈。
   聚合量：对象，由多个标量组成（User 包含 age、name），默认是聚合量。
   JVM 不会直接把整个对象塞进栈，而是标量替换：把对象拆解为多个基本变量，分散存放在栈帧的局部变量表、操作数栈，彻底取消堆上对象。
   上面 User 拆成int age、String name，name 是引用依然是标量。
   运行时没有 User 实体对象，全是零散栈变量，方法结束栈销毁，无 GC。
2. 为什么不用直接分配对象到栈？
   底层内存管理麻烦；标量拆分实现简单，效果完全等价，是 HotSpot 唯一落地方式。
   日常说的栈上分配，99% 都是标量替换。
   四、开启参数（JDK 默认配置）
   逃逸分析默认开启：
   -XX:+DoEscapeAnalysis 开启逃逸分析（JDK1.6 之后默认开启）
   -XX:+EliminateAllocations 开启标量替换（依赖逃逸分析）
   关闭：-XX:-DoEscapeAnalysis，所有对象强制堆分配。
   五、两种配套优化（基于逃逸分析）
1. 同步锁消除
   如果对象只在当前线程使用（无线程逃逸），synchronized 锁完全没必要，JIT 直接删掉锁。
   java
   运行
   public void test() {
   Object lock = new Object();
   synchronized (lock) {
   // lock只本线程用，无竞争，锁被直接消除
   }
   }
2. 无效对象消除
   没有任何使用的 new 对象，JIT 直接优化删掉，连栈都不分配。
   六、栈上分配优缺点
   优点
   完全减少堆对象数量，大幅度降低 GC 压力，减少 YGC 频次与 STW；
   栈内存随方法自动回收，无 GC 开销；
   栈访问速度高于堆，性能更好。
   限制缺点
   依赖 JIT 即时编译：解释执行不会做逃逸分析，只有代码被多次执行触发 JIT 编译才生效；冷代码无优化；
   发生逃逸就失效；
   大对象拆分后栈帧占用变大，栈容量有限，超大对象不会栈分配。
   七、常见误区纠正
   基本类型本来就在栈；栈上分配优化的是引用类型对象。
   数组很难栈分配：数组属于聚合量，JVM 一般不会拆分数组，数组几乎都是堆分配。
   ThreadLocal、成员变量、返回对象一定逃逸，不能栈分配。
   不是所有本地对象都能栈分配：循环次数少、没触发 JIT 编译，依旧堆分配。
   八、极简背诵总结
   栈上分配依托逃逸分析：对象不逃出方法 / 线程 → 不走堆；
   HotSpot 靠标量替换实现：拆解对象为基础变量存入栈，没有堆对象；
   逃逸（返回、成员变量、多线程共享）则只能堆分配；
   附带优化：锁消除、未使用对象裁剪；依赖 JIT，冷代码不生效；
   优化目标：减少堆内存占用，降低 GC。

对象的内存布局是怎样的？
在 JVM 堆中，普通对象内存分为三大部分：对象头（Header）、实例数据（Instance Data）、对齐填充（Padding）。
数组对象会多一块：数组长度。
默认开启压缩指针 -XX:+UseCompressedOops（JDK8 默认开启），下面以 64 位 JDK + 压缩指针讲解。
一、整体总览
非数组对象：对象头 + 实例数据 + 对齐填充
数组对象：对象头 + 数组长度 + 实例数据 + 对齐填充
二、对象头（最重要，分两部分：Mark Word + Klass Pointer）
1. Mark Word（标记字，8 字节）
   存储对象运行时各类标记信息，复用存储空间，根据对象状态切换存储内容：哈希值、GC 分代年龄、锁状态标记、偏向锁线程 ID、自旋锁标记。
   64 位布局拆分：
   25bit：对象 hashCode
   4bit：GC 分代年龄（最大 15，所以新生代默认年龄阈值 15）
   1bit：是否偏向锁
   2bit：锁状态（无锁、偏向锁、轻量级锁、重量级锁、GC 标记）
   不同锁状态，Mark Word 存储内容完全不一样：
   无锁：存 hash、年龄、标记位
   偏向锁：存持有偏向锁的线程 ID、偏向时间戳、年龄
   轻量级锁：存栈中锁记录指针
   重量级锁：存 monitor 监视器地址
2. Klass Pointer（类型指针）
   指向方法区元空间的 Class 模板，JVM 靠它判断对象属于哪个类。
   开启压缩指针：4 字节
   关闭压缩指针：8 字节
   非数组对象头总大小
   开启压缩：8+4=12 字节
   关闭压缩：8+8=16 字节
   补充：数组独有
   数组对象头额外多 4 字节 存储数组长度，最大支持数组长度 2^32-1。
   开启压缩：数组头 = 8+4+4=16 字节。
   三、实例数据 Instance Data
   存放真正业务内容：
   所有成员变量：当前类的字段、父类继承下来的字段；
   包含基本数据类型 + 引用类型；
   字段分配规则：
   相同宽度字段集中摆放，节省空间；
   父类字段排在子类字段前面；
   引用类型统一 4 字节（压缩指针）。
   基础类型占用（固定）
   表格
   类型	字节
   boolean	1
   byte	1
   char/short	2
   int/float	4
   long/double	8
   引用	4（压缩）/8（未压缩）
   static 静态变量不属于实例数据，存放在元空间，不在对象堆内存里。
   四、对齐填充 Padding
   HotSpot 要求：整个对象总字节数必须是 8 的整数倍。
   对象头 + 实例数据凑不齐 8 的倍数，就用 Padding 空白字节补齐，没有业务含义，只为满足内存对齐，提升 CPU 读取效率。
   举例：
   对象头 12 字节，实例数据总大小 3 字节。合计 15。离最近 8 的倍数 16 差 1，Padding 补 1 字节。
   五、举例计算（64 位，开启压缩指针）
   示例 1：空普通对象 new Object ()
   对象头：12 字节
   实例数据：无，0 字节
   合计 12，不是 8 倍数。需要补 4 字节填充。
   最终占用：16 字节。
   示例 2
   java
   运行
   class User {
   int id;    // 4
   String name;//引用4
   }
   对象头 12 + 4+4 =20。
   20 不是 8 倍数，补 4 字节，最终 24 字节。
   六、压缩指针 UseCompressedOops 作用
   开启：所有堆内引用（Klass 指针、对象引用）4 字节；堆寻址上限 32G。JDK8 默认开启。
   堆内存 >32G，压缩指针自动失效，引用变为 8 字节，对象整体变大。
   目的：节省内存，降低 GC 压力。
   七、常见高频知识点
   分代年龄存在 Mark Word，只有 4bit，最大 15，因此对象晋升老年代阈值默认 15；
   hashCode 第一次调用才计算存入 Mark Word；多次调用不再重算；
   synchronized 各类锁的核心信息全部存在 Mark Word；
   static 不在对象里，属于类；局部变量在栈，不在堆对象；
   对齐填充只保证整体是 8 的整数倍；
   数组必须记录长度，普通对象不需要。
   八、极简背诵总结
   对象三层：对象头 (MarkWord + 类型指针)、实例数据、对齐填充；数组多长度。
   MarkWord 存 hash、GC 年龄、锁信息；Klass 指针找 Class。
   实例数据存所有实例字段，静态不在此。
   Padding 凑 8 字节对齐。
   压缩指针：引用 4 字节，上限 32G；空 Object 占 16 字节。

## JVM 调优命令？
分为五大类：进程查询、内存分析、线程排查、GC 统计、堆 dump 快照，适配 Linux/Windows，线上高频使用。
所有命令格式通用：工具名 进程PID
一、jps：查 Java 进程 PID（必用入口）
jps = JVM Process Status，定位 Java 进程号，不用 ps grep 过滤。
shell
# 列出所有java进程PID+主类名
jps
# 展示PID + 完整启动参数（最实用）
jps -l
# 展示JVM启动参数
jps -v
# 展示main入参
jps -m

示例：jps -l 直接拿到 12345 com.Application
二、jstat：持续监控 GC、内存、类加载（线上常驻观测首选）
实时打印 GC 频次、内存占用、吞吐量，适合长时间观察 GC 趋势。
通用格式：jstat 选项 PID 间隔毫秒 打印次数
1）jstat -gc 最核心（推荐）
shell
# 每1000ms打印1次，无限输出；Ctrl+C停止
jstat -gc 12345 1000

字段含义：
S0C/S1C：两个 Survivor 总容量；S0U/S1U：Survivor 已用
EC/EU：Eden 总容量、已用；OC/OU：老年代总容量、已用
MC/MU：元空间；CCSC/CCSU：压缩类空间
YGC/YGCT：YGC 总次数、YGC 累计总耗时
FGC/FGCT：Full GC 次数、Full GC 总耗时
GCT：全部 GC 总耗时
2）其他常用 jstat 参数
shell
# GC容量统计（只看各区大小变化）
jstat -gccapacity PID 1000
# 查看GC百分比使用率
jstat -gcutil PID 1000
# 类加载统计：加载数量、字节、卸载数
jstat -class PID 1000
# JIT编译统计，看热点代码编译耗时
jstat -compiler PID 1000

三、jmap：堆内存快照、内存详情（OOM 排查主力）
1. 查看堆整体配置（新生代、老年代、收集器）
   shell
   jmap -heap 12345

输出：堆最大最小、Eden/Survivor 比例、使用 GC 收集器、元空间大小。
2. 查看堆内对象直方图（在线统计对象数量、占用内存）
   shell
# 打印所有类对象数量、内存占用
jmap -histo 12345
# 输出到文件，方便后续分析
jmap -histo 12345 > histo.txt

字段：序号、对象个数、占用字节、类名。可快速定位大对象。
3. 手动生成 hprof 堆 dump 文件（OOM 必做）
   shell
# 生成堆快照heap.hprof，用于MAT分析
jmap -dump:format=b,file=/data/heap.hprof 12345

生产推荐 JVM 参数自动 dump，不要等到崩了手动抓：
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/xxx/heap.hprof
4. 查看堆外内存（Direct Buffer）
   shell
   jmap -dump:live,format=b,file=live-heap.hprof PID
# live 只dump当前存活对象，体积更小

四、jstack：线程栈排查（死锁、死循环、CPU 飙高）
抓取所有线程调用栈，定位死循环、死锁、阻塞、长时间卡顿。
shell
# 导出线程栈到文件
jstack 12345 > thread.txt
# 只打印死锁信息
jstack -l 12345

高频排查场景：
CPU100%：配合top -H找到高 CPU 线程 tid，转 16 进制，在线程栈搜索定位代码；
接口阻塞、超时：查 WAITING/BLOCKED 线程；
死锁：jstack 会明确打印 Found one Java-level deadlock。
Linux 查高 CPU 线程完整流程
top 找到 Java 进程 PID
top -H -p PID 查看进程内哪个线程 CPU 最高，拿到线程十进制 tid
printf "%x\n tid" 转十六进制
jstack 导出栈，搜索 16 进制线程 ID，定位对应代码行
五、jhat：命令行解析 hprof（简陋，本地优先用 MAT）
jhat 内置 Web 服务解析堆快照，适合无图形化服务器临时兜底：
shell
jhat heap.hprof

默认端口 7000，浏览器访问查看对象引用。
缺点：性能差，大 hprof 卡顿；正式分析一律用 MAT。
六、jinfo：实时查看 / 修改 JVM 参数
不用重启，动态查看、修改部分 JVM 参数。
shell
# 查看进程全部JVM参数
jinfo 12345
# 单独查看某个参数（例如是否开启GC日志）
jinfo -flag PrintGCDetails 12345
# 动态开启GC日志（仅限可修改参数）
jinfo -flag +PrintGCDetails 12345
# 修改堆日志路径
jinfo -flag Xloggc:/data/gc.log 12345

限制：只有标注 manageable 的参数支持动态修改；Xmx/Xss 等内存参数不能改。
七、可视化工具（配套命令，方便测试环境）
jvisualvm
JDK 自带图形工具，命令行输入jvisualvm，支持远程连接、实时监控堆、线程、GC、抽样对象。
JConsole：jconsole，简单监控面板，功能弱。
八、高频线上排查组合套路
内存 OOM：jstat -gc看 GC 趋势 → jmap -histo看大对象 → jmap导出 dump，MAT 分析
CPU 打满：top→top -H→jstack 定位循环代码
接口阻塞、死锁：直接jstack -l
GC 频繁：持续jstat -gc 1000观测 YGC/FGC 上涨规律
九、常用 JVM 调优启动参数（配套命令使用）
内存基础
plaintext
-Xms4g -Xmx4g  # 堆最小最大一致，避免扩容开销
-Xmn1g         # 新生代大小
-XX:SurvivorRatio=8  # Eden:S0:S1=8:1:1
-XX:MaxMetaspaceSize=512m # 元空间上限

GC 收集器（JDK8）
plaintext
# G1
-XX:+UseG1GC -XX:MaxGCPauseMillis=200
# Parallel吞吐量收集器（默认）
-XX:+UseParallelGC
# CMS
-XX:+UseConcMarkSweepGC

辅助排查参数
plaintext
# GC日志
-XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:/gc.log
# OOM自动dump
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/heap.hprof
# 压缩指针（默认开启）
-XX:+UseCompressedOops
# 逃逸分析、栈上分配
-XX:+DoEscapeAnalysis -XX:+EliminateAllocations

十、极简背诵清单
jps 找 PID；jstat 盯 GC；
jmap 看堆、打 dump；jstack 查线程、死锁、高 CPU；
jinfo 改参数；jhat 兜底看堆；本地优先 MAT/jvisualvm；
线上标准链路：GC 异常用 jstat，OOM 抓 dump，CPU 高走 top+jstack。
