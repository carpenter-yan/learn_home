## JVM内存结构？
### 一、线程私有（每条线程独有，线程销毁内存自动回收）
1. 程序计数器（PC 寄存器）
   唯一没有OOM的内存区域。记录当前线程执行到哪一行字节码，用于线程切换后恢复执行位置。 执行native本地方法时值为空。
2. 虚拟机栈（Java 栈）
   每个方法执行都会创建一个栈帧；栈帧存放：局部变量表、操作数栈、动态链接、方法返回地址。 存放基本数据类型、对象引用地址，不存对象实体。
   异常：栈深度超过上限：StackOverflowError 栈溢出； 栈内存不断扩容耗尽：OOM。
3. 本地方法栈
   功能和虚拟机栈几乎一致，专门为 JNI Native 本地 C/C++ 方法服务，同样会栈溢出、OOM。
### 二、线程共享（全线程共用，GC重点管理）
1. 堆（Heap）
   整个JVM最大内存区域，GC主战场 所有对象、数组实例都在堆分配；
   JDK8 拆分：新生代 + 老年代；
   新生代 Eden、Survivor (S0/S1)：新建对象大多在 Eden，Minor GC 频繁；
   老年代：长期存活大对象，Full GC；
   唯一目标：存放对象，会发生堆OOM。
2. 方法区（逻辑概念）
   - JDK8彻底废除永久代，改用元空间Metaspace落地实现，直接使用本地物理内存，不在堆里。
   存放内容：类结构信息、常量池、静态变量、即时编译代码。元空间默认无固定上限，内存耗尽也会OOM。
   - 运行时常量池（属于方法区） 存放编译期字面量、符号引用，运行期也可动态存入字符串。
   - 补充：直接内存（堆外内存） 不属于JVM运行时内存，操作系统直接内存。NIO用DirectBuffer使用；不受-Xmx 限制，内存泄漏也会OOM。
### JDK7 vs JDK8 关键改动（高频考点）
   JDK7：字符串常量池从永久代挪到堆；
   JDK8：永久代PermGen彻底删除，替换为元空间 Metaspace（堆外本地内存）；永久代容易OOM，元空间更加稳定。
   垃圾回收范围总结
### 堆：GC主要回收区域；
   元空间依靠操作系统内存回收，不由GC管理；
   虚拟机栈、程序计数器随线程销毁释放，不用 GC。
### 极简背诵版
   线程私有：程序计数器、虚拟机栈、本地方法栈。计数器无OOM，栈会栈溢出。
   线程共享：堆（存对象，GC 核心）、方法区（JDK8 是元空间，存类信息、静态变量）。
   NIO使用堆外直接内存。JDK8 去掉永久代换成元空间。
### 高频配套问题
   对象存在哪里？ 对象实体在堆，引用地址在虚拟机栈局部变量表。
   栈内存回收？ 方法执行完毕栈帧自动出栈释放，不靠GC。
   元空间优势？ 使用操作系统内存，可动态扩容，大幅降低永久代OOM概率。

## 什么是JVM内存模型 ？（JMM，Java Memory Model）
注意区分：JVM运行时内存结构（堆、栈、元空间）是物理内存分区；
        JMM是并发可见性规范逻辑模型，用来解决多线程可见性、原子性、有序性。
### 一、核心定义
JMM是Java定义的一套线程与主内存交互规则，屏蔽不同操作系统CPU缓存、硬件架构差异，保证多线程并发在所有平台行为一致。
规定： 所有变量（实例字段、静态变量）存储在主内存； 每个线程拥有自己独立的工作内存（CPU 高速缓存）；
线程不能直接读写主内存，只能读写自己工作内存；必须在主存、工作内存间同步数据。
### 二、数据交互 8种操作（了解即可）
lock、unlock、read、load、use、assign、store、write。
线程修改变量流程：主存read→载入工作内存 load→修改 assign→写回主存 store+write。
### 三、JMM要解决三大并发问题
可见性 一个线程修改变量，其他线程不能立刻感知。原因：修改只改了当前线程缓存，没刷回主存。volatile、synchronized保证可见。
原子性 多线程穿插执行，简单操作被拆分。比如i++分读、改、写三步，多线程错乱。 synchronized、Atomic CAS 保证原子性。
有序性 CPU、JVM为了性能做指令重排，代码执行顺序和书写不一致，多线程出现逻辑错乱。volatile禁止指令重排；happen-before规则约束重排范围。
### 四、happen-before（先行发生）核心规则
不需要锁、volatile，只要满足先行发生，就能天然保证可见 + 有序。常用规则：
程序次序规则：单线程内，书写靠前操作先行发生于后面；
锁规则：unlock解锁一定先行发生于后续同一个锁lock加锁；
volatile规则：volatile写先行发生于后续volatile读；
线程start：start()之前代码先行发生在线程内所有操作；
线程join：线程内全部操作先行发生在join返回；
传递性：A先于B，B先于C → A先于C。
### 五、volatile在JMM的作用（高频）
保证可见性：修改立刻刷回主存，其他线程缓存失效重新拉取；禁止指令重排序；不保证原子性，无法解决i++并发问题。
### 六、JMM和JVM内存结构 极易混淆，一句话分清
JVM 运行时内存结构：物理分区（堆、虚拟机栈、元空间），是内存怎么划分存放数据；
JMM 内存模型：多线程缓存读写规范，解决并发三大特性，逻辑规则，和物理分区无关。
### 七、极简背诵版
JMM 规定变量存主内存，线程读写走自己工作缓存。解决多线程可见性、原子性、有序性。
依靠 happen-before、volatile、synchronized管控。JMM是并发规范，堆栈是物理内存分区，二者完全不是一回事。

## 垃圾对象是怎么找到的？(垃圾寻找算法)
### 一、引用计数法（了解，JVM 不用）
每个对象有引用计数器； 有引用指向它，计数器 + 1；引用失效，计数器 - 1。 计数器 = 0 → 判定垃圾可回收。
致命缺陷:无法解决循环引用。 A引用B，B引用A，二者没有外部引用。两个计数器都不为0，GC 无法回收，内存泄漏。 HotSpot JVM 不采用。
### 二、可达性分析（HotSpot 真正使用，面试核心）
以一系列GC Roots（根对象）作为起点向下遍历引用链。 能顺着引用链走到的对象：存活；GC Roots 完全遍历不到的对象：判定为垃圾，可回收。
------------------------------------------------------------------------------
## GC Roots 有哪些？
1. 虚拟机栈（Java栈）引用 方法栈帧里的局部变量、方法参数持有对象引用。只要线程还在运行，这条引用链有效。
2. 本地方法栈的 Native引用 JNI本地C/C++代码引用的Java对象。
3. 方法区（JDK8 元空间）静态变量 static修饰属性引用的对象，全局常驻。
4. 方法区常量引用 字符串常量池、运行时常量池里引用的对象。
5. 被synchronized锁住的对象 任意正在持有监视器锁的对象，一定存活。
6. JVM自身引用 Class类对象、系统类加载器加载的类； JVM内置异常、系统内部使用对象。
### 三、极简口语背诵版
栈里局部变量、Native本地引用；元空间静态变量、常量；加锁对象；JVM系统自带类与资源。以上六类作为起点，能顺着引用找到的对象存活，找不到就是垃圾。
------------------------------------------------------------------------------
## 垃圾回收器是怎样寻找GC Roots？
根可达算法是通过GC Roots来找到存活的对象的，也定义了GC Roots，那么垃圾回收器是怎样寻找GC Roots的呢？
首先，为了保证结果的准确性，GC Roots枚举时是要在STW的情况下进行的，
但是由于JAVA应用越来越大，所以也不能逐个检查每个对象是否为GC Root，那将消耗大量的时间。
一个很自然的想法是，用空间换时间，在某个时候把栈上代表引用的位置全部记录下来，
这样到真正GC的时候就可以直接读取，而不用再一点一点的扫描了。
事实上，大部分主流的虚拟机也正是这么做的，比如HotSpot，
它使用一种叫做OopMap（ordinary object pointer) 普通对象指针的数据结构来记录这类信息。
------------------------------------------------------------------------------
## OopMap是做什么的?有什么好处?
### 一、OopMap是什么
Oop = ordinary object pointer，Java对象指针。
OopMap是一张记录表，JIT编译字节码时提前生成，标记出代码指定位置里：哪些内存位置存的是对象引用，哪些是基础类型数字。
内存位置包含：虚拟机栈栈帧、寄存器。 GC不用盲目扫描整块栈内存，查表就能精准找到所有对象引用。
### 二、解决的原始痛点
如果没有OopMap：GC暂停后需要遍历每个线程整个栈所有内存，逐个判断每一段数据是不是对象指针。栈很深、线程很多，扫描极慢，拉长STW停顿。
### 三、核心好处
精准定位引用，不用全栈扫描 只读取OopMap登记好的地址，跳过int、long等普通变量，大幅加快GC Roots扫描速度，降低 STW耗时。
配合安全点Safepoint使用 只有带OopMap的代码位置是安全点。线程跑到安全点才会停下GC，此时OopMap信息完全准确，不会出现引用中途变动，保证标记不出错。
支持移动对象（标记整理、复制算法） GC移动存活对象后，需要修正所有指向该对象的指针。依靠OopMap快速找到所有栈、寄存器上的引用地址，批量更新。
### 四、补充关键点
不会每条指令都生成OopMap，只在安全点生成，节省内存；解释执行模式下没有OopMap，只有JIT编译后的机器码才有；
OopMap只负责找引用，本身不是GC Roots，只是查找GC Roots的工具。
### 极简背诵版
OopMap提前记录栈和寄存器里哪些地址是对象引用。好处是不用全栈遍历，快速扫描GC Roots，缩短 GC 停顿；
配合安全点保证引用信息可靠；方便GC移动对象后修正指针。

## 什么是安全点？什么是安全区域?
### 一、安全点 Safepoint
1. 定义 JIT编译的机器码里提前预埋的特殊代码位置。只有线程执行到安全点，JVM才能暂停线程做GC。
2. 为什么需要安全点
   线程执行到一半，栈、寄存器的引用处于不完整状态，此时GC扫描引用会标记出错；
   JIT代码只在安全点附带OopMap，非安全点没有引用清单，GC无法精准查找GC Roots。
3. 安全点主要埋点位置
   方法调用结束返回；循环每次迭代末尾；调用其他函数、抛出异常处。
4. GC等待逻辑
   JVM要GC时发出信号，运行JIT代码的线程不会立刻停下，继续执行代码，直到跑到下一个安全点主动挂起。 所有线程全部抵达安全点，进入STW，开始GC。
5. 痛点短板
   如果线程休眠、阻塞 IO、wait/sleep，线程不再执行任何代码，永远跑不到安全点，GC无限等待。这个问题靠安全区域解决。
### 二、安全区域 Safe Region
1. 适用场景
   线程长时间阻塞休眠：sleep()、wait()、阻塞 Socket IO、锁阻塞。线程停滞不动，不会执行代码，碰不到安全点。
2. 运行流程
   线程准备阻塞休眠，主动标记自己进入安全区域；线程承诺：在安全区域全程不会修改任何对象引用，引用状态稳定；
   JVM收到标记，可以直接执行GC，不用等待线程跑安全点； 线程睡醒、要退出阻塞时，先检查GC有没有执行完毕：
   GC已经结束：线程正常恢复运行；GC还在进行：线程原地等待，直到GC结束再继续。
3. 本质 安全区域是静态的安全状态；安全点是动态代码位置。
### 三、核心对比表

   维度|安全点 Safepoint|安全区域 Safe Region
    --|--|--
   使用线程|正常跑 CPU 代码、不停执行指令的线程|sleep/wait/IO 阻塞、暂停运行的线程
   触发方式|代码执行走到预设点位|线程主动给自己打标记
   依赖|JIT + OopMap|无 OopMap 依赖，靠线程主动保证引用不变
   能否随时 GC|不行，必须走到点位|可以，标记后随时能 GC

### 四、执行模式补充区分
   JIT编译代码：严格依赖安全点；解释执行：没有安全点限制，每条字节码结束都能GC，基本用不到安全区域；
   安全点、安全区域都是HotSpot为JIT代码设计的配套机制。
### 五、极简背诵话术
   安全点是正常运行代码里的固定点位，JIT线程必须跑到这里才能停下GC，配套OopMap；
   线程休眠、阻塞跑不到安全点，用安全区域，线程标记自己不再改引用，JVM可直接GC；
   安全点管运行中的线程，安全区域管阻塞休眠的线程。

## 什么是 STW ? 为什么需要 STW ?
### 一、STW 定义
STW = Stop-The-World，全世界暂停。
执行GC时，所有Java业务用户线程全部冻结停止执行，只有GC工作线程正常运行；GC全部结束后，再恢复所有业务线程。
不管G1、CMS、ZGC、Shenandoah，所有垃圾收集器都存在STW，只是停顿长短差别极大。
### 二、必须 STW 的核心原因（4条必背）
1. 防止引用不断变化，标记错乱
   GC做可达性分析遍历引用链时，如果业务线程还在运行：一边GC标记对象，一边业务代码新增引用、删除引用、修改引用地址。
   会出现两种严重错误： 1）漏标：存活对象被误当成垃圾回收，程序空指针崩溃；2）多标：垃圾被当成存活，无法回收，内存泄漏。
   暂停所有业务线程，引用关系完全静止，标记绝对准确。
2. 配合OopMap、安全点，稳定查找GC Roots
   JIT代码仅在安全点拥有OopMap。线程停在安全点后，栈、寄存器引用固定，依靠OopMap精准取出GC Roots。
   如果线程继续跑，栈数据实时变动，OopMap瞬间失效，没法定位引用。
3. 支持复制/标记整理：移动对象必须修正指针
   复制算法、标记整理会把存活对象在堆中搬家。对象地址改变后，所有栈、静态变量里的引用地址都要统一更新。
   只有业务线程全部停下，才能批量修改指针；若线程一边运行一边改地址，代码访问对象会拿到旧地址，内存访问异常。
4. 保证卡表、跨代引用标记稳定
   MinorGC依靠卡表记录老年代引用新生代。用户线程不停的话，老年代引用随时新增/消失，卡表数据错乱，导致新生代漏标。STW 保证卡表信息固定。
### 三、误区澄清
   STW不是JVM 缺点，是正确性兜底方案；低延迟收集器（ZGC）只是把绝大部分耗时操作并发执行，只保留极短微秒级 STW，做不到完全无STW。
   只有用户线程停止，GC自己的工作线程全程正常跑。
### 四、CMS、G1、ZGC 如何优化 STW 时长
   CMS：并发标记大部分阶段不用 STW，仅初始标记、重新标记两段短暂停顿；
   G1：全程分多段小STW，可设置最大停顿时间；
   ZGC：几乎所有工作并发执行，仅残留几十微秒级STW。
### 五、安全点和 STW的联动
   JIT线程不会被强制中断，需要等待全部线程走到安全点，统一进入STW；阻塞线程依靠安全区域提前就位。所有线程就位，才正式开始GC。
### 六、极简背诵版
   STW是GC时暂停全部业务线程。
   必要性：引用不再变动保证标记准确；配合OopMap找GC Roots；移动对象可以安全修改指针；保证卡表有效。
   所有GC都有STW，优秀收集器只是缩短停顿，无法彻底消除。

## 四种引用类型？
1. 强引用 StrongReference（最常用）
   日常编码普通对象引用：Object obj = new Object();
   规则 只要这条GC可达的强引用存在，GC永远不会回收该对象，哪怕内存爆满OOM。
   回收条件 手动把引用置为null、引用走出作用域（方法结束栈帧销毁），强引用断掉，对象才会被当做垃圾。
   场景 绝大多数业务对象、实体、集合、本地变量全部是强引用。
2. 软引用 SoftReference
   用法：SoftReference<Object> soft = new SoftReference<>(new Object());
   规则 堆内存充足：GC不会回收；内存紧张、快要发生OOM时，一定会回收软引用指向的对象；回收后如果内存依旧不够，才抛出OOM。
   典型用途 做内存友好缓存（图片缓存、本地大缓存），内存够就缓存加速，内存不足自动释放兜底。
3. 弱引用 WeakReference
   用法：WeakReference<Object> weak = new WeakReference<>(new Object());
   规则 只要触发 GC，不管内存够不够，弱引用指向的对象必然被回收。 生命周期只能撑到下一次GC。
   高频场景 ThreadLocalMap的key使用弱引用，避免线程长期持有ThreadLocal造成内存泄漏；各种缓存、WeakHashMap。
4. 虚引用 PhantomReference（幽灵引用）
   用法：必须搭配引用队列ReferenceQueue，不能单独使用。
   规则 无法通过get()拿到对象，形同没有引用；对象被GC销毁前，虚引用会被丢入队列；只能用来感知回收事件，不能操作对象。
   唯一作用 堆外内存（NIO DirectBuffer）资源释放、文件句柄、底层资源的善后清理； 监控对象何时被回收，做资源收尾。
### 快速对比总结表

   引用类型|GC 回收时机|能否 get 拿到对象|核心用途
    --|--|--|--
   强引用|引用断开才回收|可以|正常业务开发
   软引用|内存不够才回收|可以|可清理缓存
   弱引用|只要 GC 就回收|可以|ThreadLocal、WeakHashMap
   虚引用|回收入队列通知|get 永远返回 null|堆外内存、资源释放

### 极简背诵口诀
   强引用：有引用绝不回收； 软引用：内存不够才回收； 弱引用：一次GC必回收； 虚引用：拿不到对象，只做回收通知。
### 高频面试必问：ThreadLocal为什么key用弱引用？
   ThreadLocal对象不用时，外部强引用清空，但线程池线程长期存活，线程的ThreadLocalMap还持有key。
   key是弱引用：下次GC自动回收key，Entry只剩value，后续清理可以释放value，防止内存泄漏。
   value依旧是强引用，所以用完最好手动remove。
