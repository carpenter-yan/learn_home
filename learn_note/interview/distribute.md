## 分布式系统原理？
分布式系统完整原理（后端面试体系化讲解）
一、分布式定义
把一个大型单体应用拆分成多个独立节点/服务，节点分布在不同服务器、机房，通过网络互相通信协作，对外整体提供服务。
和单体区别：单体所有模块在一台机器，共享内存、数据库；分布式多机器靠网络交互，天然带来网络不可靠、数据一致性、时序、故障等一堆新问题。
常见分布式形态
微服务分布式：按业务拆分（会员、订单、支付、库存独立服务）；
存储分布式：Redis集群、MySQL分库分表、ES集群；
计算分布式：大数据Hadoop、Flink多节点并行计算。
### 二、分布式核心痛点（CAP、BASE 是底层理论基石）
1. CAP定理（分布式不可能三者同时满足）
   C 一致性 Consistency：所有节点同一时刻数据完全一致。A 节点更新完，B、C 节点查询必须拿到最新值。
   A 可用性 Availability：任意节点故障，整体服务依旧能正常响应请求。
   P 分区容错 Partition Tolerance：网络故障、机房断网、丢包，节点之间网络不通。
   现实网络一定会出问题，P必选，只能在C和A之间二选一：
   CP 架构：放弃可用性，保证强一致。代表：Zookeeper。网络分区时阻塞请求，等待通信恢复，保证数据一致；
   AP 架构：放弃强一致性，保证服务可用。代表：Eureka、Nacos、Redis集群。网络断了节点各自对外提供服务，数据最终同步。
2. BASE理论（互联网主流落地，CAP的工程妥协）
   互联网业务几乎不用强一致，遵循BASE，最终一致性：
   Basically Available 基本可用：故障不会整体雪崩，可能降响应、限流，不会彻底挂掉；
   Soft state 柔性状态：节点数据允许短暂不一致，中间状态不用统一；
   Eventually consistent 最终一致性：经过一段时间同步，所有节点数据最终一致。
   订单、缓存、MQ全部是最终一致性。
### 三、分布式必须解决的7大基础问题 + 落地方案
1. 分布式会话（Session 共享）
   单体：tomcat本地存session；分布式多服务请求落在不同机器，session丢失。
   方案：统一存入Redis，所有服务读写Redis实现会话共享；现在主流用JWT无token，不用存服务端。
2. 分布式ID（全局唯一主键）
   多节点同时插入数据库，自增主键重复。
   常见方案：
   雪花算法Snowflake（MP 默认）：时间戳 + 机器号 + 序列号，本地生成，无中心化；
   Redis自增：incr生成 ID；
   数据库号段模式；
   UUID（无序，索引性能差）。
3. 分布式事务（跨库 / 跨服务保证原子性）
   本地事务只管控单个库；分布式一次操作涉及订单库、库存库、支付库，要么全成功，要么全失败。
   主流方案分层：
   2PC（两阶段提交，强一致）
   准备阶段：所有资源锁定、预执行；提交阶段全部确认提交，任一失败全部回滚。
   缺点：阻塞严重，协调者故障卡死，性能差，适合金融。Seata AT 底层就是改良 2PC。
   TCC（Try-Confirm-Cancel）侵入代码
   Try 预留资源；Confirm 确认执行业务；Cancel 补偿回滚。代码侵入高，适合高可靠资金场景。
   本地消息表 + 可靠 MQ（最终一致，互联网最常用）
   本地事务操作业务 + 落消息表；MQ 异步发消息，下游消费；消费失败不断重试；保证最终一致。无锁、高性能。
   Seata AT 模式：无侵入，自动生成 undo_log 回滚日志，业务代码不用改动，日常微服务首选。
4. 分布式锁（多服务并发争抢资源）
   单机用 synchronized、ReentrantLock；多节点 JVM 锁互不生效。
   主流实现：
   Redis 分布式锁（SETNX+EXPIRE；RedLock；Redisson）；
   Zookeeper 临时节点锁；
   MySQL 乐观锁 @Version、悲观锁 for update。
5. 远程服务通信
   服务拆分开无法本地调用，依靠网络调用：
   同步调用：OpenFeign、RestTemplate、JSF、Dubbo；
   异步解耦：RocketMQ/Kafka，削峰、异步、流量隔离。
6. 服务注册发现
   服务IP不固定，调用方不知道目标服务地址。
   架构：注册中心 (Nacos/Eureka/ZK)
   服务提供者启动上报 IP、端口；
   消费者定期拉取服务节点列表；
   调用时负载均衡选节点。
7. 负载均衡
   多实例服务，请求均匀分发：
   客户端负载均衡：Ribbon，本地维护节点列表自己做轮询、随机、权重；
   服务端负载均衡：Nginx、网关Gateway统一转发。
### 四、分布式高可用保障体系
限流：网关 / 服务层限制 QPS，防止流量压垮集群；
熔断降级：调用方Sentinel/Resilience4j，下游故障切断调用，兜底防雪崩；
集群多副本：所有服务、Redis、MySQL 多实例，节点挂了其他节点顶替；
重试 + 幂等：网络抖动重复调用，保证接口幂等（唯一键、状态机、防重表），重试不会重复扣款、重复下单；
超时控制：所有远程调用必须设超时，避免线程无限阻塞。
### 五、分布式数据一致性细分
强一致性：任何时刻全节点数据一模一样（Zookeeper）；
最终一致性：短暂不一致，后台异步同步，最终统一（MySQL 主从、Redis、MQ）；
读写分离：主库写，从库读，存在主从延迟，典型最终一致；
分库分表：Sharding-JDBC，水平拆分海量数据，带来分布式事务、跨表分页、排序新问题。
### 六、全链路极简运行流程（微服务分布式举例）
用户下单：网关 → 订单服务 → 库存服务 + 支付服务
所有服务注册到Nacos；网关通过注册中心拿到所有服务地址；
订单远程调用库存、支付，OpenFeign负载均衡；
分布式锁扣库存，防止超卖；
Seata保证订单、库存、支付分布式事务最终一致；
调用方加Sentinel熔断，库存超时走降级；
所有接口限流防突发流量；
ID使用雪花算法全局唯一；
异步通知短信用MQ，解耦。
### 七、面试背诵精简版
分布式就是多机器节点通过网络协作提供服务。底层遵循 CAP 与 BASE，网络分区不可避免，业务大多选择AP最终一致性。
日常开发要解决八大问题：注册发现、远程调用、分布式ID、分布式锁、分布式事务、会话共享、负载均衡、高可用防护（限流熔断降级）。
主流靠Nacos/Dubbo做服务治理，Seata管控事务，Redis实现分布式锁，MQ异步解耦，整套架构保证集群高可用、可扩容。
