## 什么是Spring?
Spring是一套轻量级Java全栈开源开发框架，诞生目的：解决早期Java EE（EJB）臃肿、笨重、开发繁琐、耦合度极高的痛点。
它不是单一功能框架，是一整套生态家族，核心目标：解耦、简化开发、方便测试、适配各种中间件/数据库/微服务。
绝大多数Java后端项目（单体、SpringBoot、微服务 SpringCloud）底层都基于Spring。
------------------------------------------------------------------------------
## 用到哪些设计模式?
1. 工厂模式: 比如通过BeanFactory和ApplicationContext来生产Bean对象
2. 代理模式: AOP的实现方式就是通过代理来实现，Spring主要是使用JDK动态代理和CGLIB代理
3. 单例模式: Spring中的Bean默认都是单例的
4. 模板模式: Spring中jdbcTemplate等以Template结尾的对数据库操作的类，都会使用到模板方法设计模式，一些通用的功能
5. 包装器模式: 我们的项目需要连接多个数据库，而且不同的客户在每次访问中根据需要会去访问不同的数据库。这种模式让我们可以根据客户的需求能够动态切换不同的数据源
6. 观察者模式: Spring事件驱动模型观察者模式的
7. 适配器模式: Spring AOP的增强或通知(Advice)使用到了适配器模式
------------------------------------------------------------------------------
## 哪些核心模块?
- Spring Core：Spring核心，它是框架最基础的部分，提供IOC和依赖注入DI特性
- Spring Context：Spring上下文容器，它是BeanFactory功能加强的一个子接口
- Spring Web：它提供Web应用开发的支持
- Spring MVC：它针对Web应用中MVC思想的实现
- Spring DAO：提供对JDBC抽象层，简化了JDBC编码，同时，编码更具有健壮性
- Spring ORM：它支持用于流行的ORM框架的整合，比如：Spring + Hibernate、Spring + iBatis、Spring + JDO的整合等
- Spring AOP：即面向切面编程，它提供了与AOP联盟兼容的编程实现
------------------------------------------------------------------------------
## Bean的作用域?
1、singleton: 唯一bean 实例，Spring中的bean默认都是单例的。
2、prototype: 每次请求都会创建一个新的bean实例。
3、request: 每一次HTTP请求都会产生一个新的bean，该bean仅在当前HTTP request内有效。
4、session: 在一个HTTP Session中，一个Bean定义对应一个实例。该作用域仅在基于web的 Spring ApplicationContext情形下有效。
5、global-session：全局session作用域，仅仅在基于portlet的web应用中才有意义，Spring5已经没有了。

## BeanFactory和FactoryBean区别?
1. BeanFactory：IOC 顶层容器，所有 Bean 的管理者，ApplicationContext 是它的增强实现；懒加载。
2. FactoryBean：特殊 Bean，用于构建创建复杂的对象；靠 getObject 返回最终 Bean。

维度|BeanFactory|FactoryBean
--|--|--
身份|Spring 容器顶层工厂，IOC 本体|一个特殊业务 Bean，用来生成别的对象
职责|管理容器内全部 Bean|只生产某一个复杂对象
使用方|Spring 框架底层使用|开发人员自定义实现
获取方式|通过 ApplicationContext / 容器使用|自己写类实现接口，注册到 Spring
获取本身|正常 getBean 拿容器|加 & 前缀：getBean("&xxx")拿到 FactoryBean 本身；不加 & 拿到 getObject 返回的对象
典型例子|ClassPathXmlApplicationContext|MapperFactoryBean、Redis 连接池工厂

# BeanFactory和ApplicationContext区别 ?
1、BeanFactory 可以理解为含有bean集合的工厂类。BeanFactory包含了种bean的定义，以便在接收到客户端请求时将对应的bean实例化。 
    BeanFactory还能在实例化对象的时生成协作类之间的关系。此举将bean自身与bean客户端的配置中解放出来。
    BeanFactory还包含了bean生命周期的控制，调用客户端的初始化方法（initialization methods）和销毁方法（destruction methods）。
2、application context 如同bean factory一样具有bean定义、bean关联关系的设置，根据请求分发bean的功能。
    但ApplicationContext在此基础上还提供了其他的功能：支持国际化的文本消息；统一的资源文件读取方式；监听器中注册bean的事件

## 什么是XMLBeanFactory？
XmlBeanFactory根据XML文件中的定义加载beans。该容器从XML文件读取配置元数据并用它去创建一个完全配置的系统或应用。

## @Repository、@Service、@Component、@Controller它们有什么区别?
这四个注解的本质都是一样的，都是将被该注解标识的对象放入Spring容器当中，只是为了在使用上区分不同的应用分层
@Repository: 对应持久层即Dao层，主要用于数据库相关操作
@Service: 对应服务层，主要涉及一些复杂的逻辑，需要用到Dao层
@Controller: 对应Spring MVC控制层，主要用户接受用户请求并调用Service层返回数据给前端页面
@Component: 其他不属于以上三层的统一使用该注解
------------------------------------------------------------------------------
## @Autowired和@Resource有什么区别?
@Resource是Java自己的注解，@Resource有两个属性是比较重要的，分是name和type；Spring将@Resource注解的name属性解析为bean的名字，而type属性则解析为bean的类型。
    所以如果使用name属性，则使用byName的自动注入策略，而使用type属性时则使用byType自动注入策略。如果既不指定name也不指定type属性，这时将通过反射机制使用byName自动注入策略。
@Autowired是spring的注解，是spring2.5版本引入的，Autowired只根据type进行注入，不会去匹配name。如果涉及到type无法辨别注入对象时，那需要依赖@Qualifier或@Primary注解一起来修饰。

## IOC是什么?
IOC(Inversion of Control)负责创建对象，管理对象（通过依赖注入（DI），并且管理这些对象的整个生命周期。它的核心思想就是控制反转。

------------------------------------------------------------------------------
## 控制反转是什么?
控制反转就是说，把对象的控制权交给了spring，由spring容器进行管理，我们不进行任何操作

------------------------------------------------------------------------------
## 为什么需要控制反转?
没有控制反转的时候，我们需要自己去创建对象，配置对象，还要人工去处理对象与对象之间的各种复杂的依赖关系，当一个工程的代码量很大时，这种关系的维护是非常令人头痛的，
所以就有了控制反转这个概念，将对象的创建、配置等一系列操作交给Spring去管理，不需要⼈⼯来管理对象之间复杂的依赖关系。

------------------------------------------------------------------------------
## IOC容器有哪些?
Spring主要提供了两种IOC容器，一种是BeanFactory，还有一种是ApplicationContext
它们的区别，BeanFactory只提供了最基本的实例化对象和拿对象的功能，
而ApplicationContext是继承了BeanFactory所派生出来的产物，是其子类，它的作用更加的强大，比如支持注解注入、国际化等功能

------------------------------------------------------------------------------
## DI 是什么?
DI(Dependency Injection)就是依赖注入，其实和IOC大致相同，只不过是同一个概念使用了不同的角度去阐述
DI所描述的重点是在于依赖，我们说了IOC的核心功能就是在于在程序运行时动态的向某个对象提供其他的依赖对象，
而这个功能就是依靠DI去完成的，比如我们需要注入一个对象A，而这个对象A依赖一个对象B，那么我们就需要把这个对象B注入到对象A中，这就是依赖注入。
控制反转是一种思想，依赖注入是实现方式！
Spring 有三种注入方式:
- 接口注入
- 构造器函数注入
- setter注入

------------------------------------------------------------------------------
## AOP是什么?
AOP意为：面向切面编程，通过预编译方式和运行期间动态代理实现程序功能的统一维护的一种技术。
AOP是 OOP(面向对象编程) 的延续，是Spring框架中的一个重要内容，是函数式编程的一种衍生范型。
利用AOP可以对业务逻辑的各个部分进行隔离，从而使得业务逻辑各部分之间的耦合度降低，提高程序的可重用性，同时提高了开发的效率。

AOP实现主要分为两类:

静态AOP实现，AOP框架在编译阶段对程序源代码进行修改，生成了静态的AOP代理类（生成的 *.class文件已经被改掉了，需要使用特定的编译器），比如 AspectJ
动态AOP实现， AOP框架在运行阶段对动态生成代理对象（在内存中以JDK 动态代理，或CGlib动态地生成AOP代理类），如 SpringAOP
Spring中AOP的实现是通过动态代理实现的，如果是实现了接口就会使用JDK动态代理，否则就使用CGLIB代理。
有5种通知类型:
- @Before:目标方法运行之前执行。
- @AfterReturning:目标方法正常成功执行完毕、return返回后执行。
- @AfterThrowing:目标方法抛出异常时执行。
- @After:无论目标正常结束、还是抛异常，最后一定执行。
- @Around:包裹整个目标方法，在方法调用前后都能自定义逻辑，手动控制目标方法要不要执行。
------------------------------------------------------------------------------
## 动态代理和静态代理有什么区别?
静态代理
- 由程序员创建或由特定工具自动生成源代码，再对其编译。在程序运行前，代理类的.class文件就已经存在了
- 静态代理通常只代理一个类
- 静态代理事先知道要代理的是什么

动态代理
- 在程序运行时，运用反射机制动态创建而成
- 动态代理是代理一个接口下的多个实现类
- 动态代理不知道要代理什么东西，只有在运行时才知道
------------------------------------------------------------------------------
# JDK动态代理和CGLIB代理有什么区别？
1. JDK动态代理时业务类必须要实现某个接口，它是基于反射的机制实现的，生成一个接口的代理子类，通过重写方法，实现对代码的增强。
   只能代理实现了接口的类。基于接口生成代理类，没有接口无法使用。
2. CGLIB动态代理是使用字节码处理框架ASM，其原理是通过字节码技术为一个类创建子类，然后重写父类的方法，实现对代码的增强。
   不需要接口，通过继承目标类生成子类作为代理；重写目标类非final方法实现增强。

------------------------------------------------------------------------------
## Spring AOP 和 AspectJ AOP 有什么区别？
Spring AOP是运行时增强，是通过动态代理实现的
AspectJ AOP是编译时增强，需要特殊的编译器才可以完成，是通过修改代码来实现的，支持三种织入方式
- 编译时织入: 就是在编译字节码的时候织入相关代理类
- 编译后织入: 编译完初始类后发现需要 AOP 增强，然后织入相关代码
- 类加载时织入: 在加载器加载类的时候织入

主要区别|Spring AOP|AspecjtJ AOP
--|--|--
增强方式|运行时增强|编译时增强
实现方式|动态代理|修改代码
编译器|javac|特殊的编译器 ajc
效率|较低(运行时反射损耗性能)|较高
织入方式|运行时|编译时、编译后、类加载时

## Bean生命周期?
整体流程：实例化 → 属性填充 → 初始化 → 使用 → 销毁，细分标准全流程，同时标注所有扩展点。
### 一、完整标准执行步骤
1. **实例化Instantiation**
Spring 通过反射创建Bean对象（调用构造方法）。 分为单例容器启动创建、多例每 getBean才创建。
2. **属性赋值Populate Bean**
依赖注入：通过字段/setter给属性赋值，完成 @Autowired、普通属性、配置值注入。
3. Aware接口回调（各类感知接口）
  Spring把容器资源注入Bean，拿到Spring底层对象；常用：
- BeanNameAware：拿到当前 Bean 的名字
- BeanFactoryAware：拿到IOC 容器工厂
- ApplicationContextAware：拿到上下文ApplicationContext
4. Bean后置处理器 BeforeInitialization
  BeanPostProcessor.postProcessBeforeInitialization
  所有Bean初始化之前统一拦截，可修改包装Bean。
  Spring AOP就是在这里生成代理对象。
5. **初始化Initialization（三类初始化任选）**
  优先级顺序：@PostConstruct → InitializingBean 接口 afterPropertiesSet → XML init-method
  - @PostConstruct 注解（注解方式，开发最常用）
  - 实现InitializingBean 接口，重写 afterPropertiesSet()
  - xml/配置指定 init-method 自定义初始化方法
6. Bean后置处理器AfterInitialization
  BeanPostProcessor.postProcessAfterInitialization
  初始化全部完成后执行；如果第四步没创建代理，这里也可做代理。
  **至此：Bean 完全就绪，可以交给业务使用。**
7. **正常使用阶段**
  程序员@Autowired注入，调用执行业务逻辑；单例常驻容器。
8. **容器关闭触发销毁Destruction**
  容器close()/ 优雅停机时执行销毁逻辑，仅限单例Bean；prototype多例Spring不管理销毁。
  销毁三种方式优先级：
  @PreDestroy → DisposableBean接口destroy() → XML destroy-method
9. Bean彻底回收
  对象无引用，等待JVM垃圾回收。
### 二、极简流程串记
实例化 → 填属性 → Aware → 前置后置处理器（前）→ 初始化 → 后置处理器（后）→ 使用 → 容器关闭销毁

## Spring 怎么解决循环依赖?
循环依赖就是说两个对象相互依赖，形成了一个环形的调用链路
Spring 使用三级缓存去解决循环依赖，其核心逻辑就是把实例化和初始化的步骤分开，然后放入缓存中，供另一个对象调用
- 第一级缓存：用来保存实例化、初始化都完成的对象
- 第二级缓存：用来保存实例化完成，但是未初始化完成的对象
- 第三级缓存：用来保存一个对象工厂，提供一个匿名内部类，用于创建二级缓存中的对象

当 A、B 两个类发生循环引用时 大致流程
1. A 完成实例化后，去创建一个对象工厂，并放入三级缓存当中
如果 A 被 AOP 代理，那么通过这个工厂获取到的就是 A 代理后的对象
如果 A 没有被 AOP 代理，那么这个工厂获取到的就是 A 实例化的对象
2. A 进行属性注入时，去创建 B
3. B 进行属性注入，需要 A ，则从三级缓存中去取 A工厂代理对象并注入，然后删除三级缓存中的 A工厂，将 A对象放入二级缓存
4. B 完成后续属性注入，直到初始化结束，将 B放入一级缓存
5. A 从一级缓存中取到B并且注入B， 直到完成后续操作，将A从二级缓存删除并且放入一级缓存，循环依赖结束

Spring 解决循环依赖有两个前提条件：
1. 不全是构造器方式的循环依赖 (否则无法分离初始化和实例化)
2. **必须是单例 **(否则无法保证是同一对象)

------------------------------------------------------------------------------
## 为什么要使用三级缓存，二级缓存不能解决循环依赖吗？
### 一、先回顾循环依赖场景
循环依赖：A 依赖 B，B 又依赖 A。
Spring 默认单例、字段注入（@Autowired）会出现循环依赖。
Spring 解决setter / 字段注入循环依赖依靠三级缓存；构造器注入循环依赖无法解决。
三级缓存全部存于 DefaultSingletonBeanRegistry：
一级缓存 singletonObjects：完整就绪、初始化完毕的最终单例 Bean（成品）
二级缓存 earlySingletonObjects：提前曝光的半成品 Bean（已经实例化，还没填充属性、没初始化）
三级缓存 singletonFactories：存放 ObjectFactory，用来生成 Bean 的早期代理对象
### 二、只用二级缓存行不行？分两种情况
#### 情况 1：所有 Bean 都不需要 AOP 代理（无事务、无切面）
只需要一级 + 二级缓存就能搞定循环依赖，三级缓存完全多余。
流程演示：
创建 A，实例化完成，属性还没注入，把半成品 A 放入二级缓存；
A 填充属性需要 B，开始创建 B；
B 实例化完成，放入二级缓存；B 填充属性需要 A；
从二级缓存拿到半成品 A，完成 B 的属性注入，走完 B 完整生命周期，B 存入一级缓存；
回到 A，属性注入完成，A 初始化，放入一级缓存，二级清掉。
无代理时，二级缓存足够。
#### 情况 2：存在 AOP 代理（加了 @Transactional、切面），只用二级缓存会严重 bug
这就是必须加三级缓存的根本原因。
矛盾点
正常时机：AOP 代理在BeanPostProcessor初始化之后才创建；
循环依赖：A 还没走到初始化，属性填充阶段就需要把 A 暴露给 B。
如果只用二级缓存：
存入二级缓存的是原生普通对象；
B 注入拿到原生对象；
后续 A 走完初始化，才生成代理对象放入一级缓存；
最终：B 持有的是原生裸对象，容器里最终是代理对象，两个对象不一致，事务、AOP 全部失效。
### 三、三级缓存的核心作用：延迟生成代理
三级缓存存的是 ObjectFactory 对象工厂，不是 Bean 本身。
工厂内部封装：如果需要代理就返回代理，不需要代理返回原对象。
完整正确流程（带事务 A）：
实例化 A，此时还没属性填充、没初始化；向三级缓存存入 A 的 ObjectFactory。
A 需要 B，创建 B；B 需要 A。
发现 A 在三级缓存，调用 ObjectFactory.getObject ()：
需要 AOP 就生成代理；无代理返回原生对象。
拿到的代理对象放入二级缓存，删除三级缓存。
B 注入代理 A，B 正常走完流程，存入一级缓存。
A 继续完成属性填充、初始化、创建最终代理，存入一级缓存。
保证：B 拿到的 A，和最终容器中的 A 是同一个代理对象。
三级缓存各司其职
一级：最终成品 Bean，对外正常获取；
二级：缓存已经通过工厂生成好的早期 Bean（代理 / 原生），避免重复调用工厂创建代理；
三级：存放工厂，实现「需要暴露的时候才动态创建代理」，不用提前生成。
### 四、为什么不能提前统一生成代理放到二级？
Spring 设计原则：代理统一在初始化后创建，大部分 Bean 不需要循环依赖，没必要提前生成代理；提前创建会打乱整个 Bean 生命周期顺序；
只有发生循环依赖时，才被迫提前生成代理；没有循环依赖，正常走完生命周期后置处理器再生成代理。
三级缓存实现按需动态生成，兼顾正常 Bean 生命周期 + 循环依赖代理一致性。
### 五、关键总结：二级缓存的短板
无 AOP 代理：二级缓存够用；
有 AOP（事务、切面）：只用二级缓存，依赖方拿到原生对象，容器是代理对象，对象不一致，AOP 失效；
三级缓存依靠 ObjectFactory 实现按需生成早期代理，保证循环依赖场景所有地方拿到的是同一个代理；
多例、构造器注入循环依赖 Spring 无法解决，和三级缓存无关。
### 六、极简背诵版
无AOP代理，二级缓存可以解决循环依赖；有AOP 代理，二级缓存会出现原生对象和代理对象不一致。
三级缓存存放ObjectFactory工厂，循环依赖触发时动态生成代理，保证所有地方拿到同一个代理。
正常Bean代理在初始化后创建；循环依赖被迫提前生成，三级缓存适配两种场景。
二级缓存存已经生成好的早期Bean；三级缓存是生成Bean的工厂，实现懒代理。

## 事务的传播规则?
### 基础概念
传播行为：当前方法调用别的带事务的方法时，两个事务如何合并、创建、挂起。
标注位置：@Transactional(propagation = Propagation.XXX)
分为三类：新建事务、复用当前事务、不使用事务。
调用模型：外层方法A调用内层方法B，分别配置传播属性。
### 7 种传播行为逐条详解
1. REQUIRED（默认，最常用）
   有当前事务就加入；没有则新建事务
   - A 有事务：B 融入 A 的同一个事务。任意一方异常，整体一起回滚。
   - A 无事务：B 新开独立事务。
   业务绝大多数场景使用：订单、扣费。
2. SUPPORTS
   支持当前事务：有就共用，没有就非事务运行
   - A 有事务：B 共用事务；
   - A 无事务：B 无事务执行，报错不会回滚。
   适合查询类，有事务跟着事务走，没事务裸跑。
3. MANDATORY（强制必须有事务）
   必须外层存在事务，否则直接抛异常
   - A 有事务：B 加入；
   - A 无事务：抛出异常，拒绝执行。
   用于强制上层必须开启事务，防止漏事务。
4. REQUIRES_NEW
   每次都新建独立事务，外层事务挂起 
   无论外层有没有事务，B 都新开专属事务；外层事务暂停。
   - A 报错回滚，B 不受影响；
   - B 异常回滚，A 也不受影响。
   典型场景：日志记录、操作留痕。主业务失败，日志依然入库。
5. NOT_SUPPORTED
   不支持事务，外层事务挂起，以非事务执行
   外层有事务也被挂起，B 全程无事务。
   适合大批量查询、统计，不需要事务，避免长事务锁表。
6. NEVER
   绝对禁止有事务，外层有事务直接报错
   - A 有事务：抛异常；
   - A 无事务：正常无事务执行。
   严格禁止事务环境，极少使用。
7. NESTED 嵌套事务
   外层有事务：开启嵌套子事务；外层无事务则新建事务
   关键点：
   - 依赖数据库保存点（MySQL InnoDB 支持）；
   - 内层 B 回滚只回滚自己，不影响外层 A；
   - 外层 A 回滚，连带所有嵌套子事务一起回滚。
   和 REQUIRES_NEW 区别：嵌套共用外层连接，外层回滚子事务必回滚；新事务完全独立。
   适合批量操作，子步骤可单独回滚，整体失败全部回退。
### 高频易错对比
   REQUIRES_NEW vs NESTED
    - REQUIRES_NEW：完全独立，互不影响；
    - NESTED：子事务依附父事务，父回滚子必回滚，子回滚父不受影响。
   REQUIRED 整体同事务：任意位置异常，全量回滚。
### 典型业务落地搭配
   扣费、下单：REQUIRED；
   查询接口：SUPPORTS；
   操作日志：REQUIRES_NEW（主流程失败日志仍保存）；
   批量统计：NOT_SUPPORTED；
   批量分步骤，允许单步回滚：NESTED。
### 极简背诵口诀
   REQUIRED 默认，有就共用无就新建；
   SUPPORTS 随缘，有事务用事务，没有裸跑；
   MANDATORY 必须上层有事务，否则报错；
   REQUIRES_NEW 必开新事务，内外互不干扰；
   NOT_SUPPORTED 挂起事务，裸跑；
   NEVER 不许有事务，有则报错；
   NESTED 嵌套，子可单独回滚，父回滚子全回。
