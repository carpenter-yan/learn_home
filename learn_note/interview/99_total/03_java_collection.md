# Java 集合・9 张实战卡（按主线顺序）

## 主线：数据怎么又快又省地存取

```
① 底层怎么存      → 数组 vs 链表（ArrayList / LinkedList）
② 怎么快速定位    → 哈希表（HashMap 的数组 + 桶）
③ 冲突了怎么办    → 链表 → 红黑树（JDK8 树化）
④ 扩容怎么搬      → resize、2 的幂、高低位拆分
⑤ 有序怎么办      → TreeMap / 红黑树
⑥ 并发怎么安全    → ConcurrentHashMap
⑦ 遍历怎么防篡改  → fail-fast / modCount
```

### 卡 1　ArrayList vs LinkedList　★★★

**关键词**：数组 / 双向链表 / 随机访问 / 内存局部性

**串线**：主线第 ① 环「底层怎么存」

**Q1 定义（20%）**

- ArrayList 底层是**动态数组**，支持 O (1) 随机访问。
- LinkedList 底层是**双向链表**，插入删除 O (1)，但随机访问 O (n)。
- 实际业务里 **ArrayList 用得更多**。

**Q2 场景（50%）**

面试官问：为什么大家都用 ArrayList，LinkedList 明明插入快？

- LinkedList 每次插入要**新建 Node 对象**，内存开销大。
- 节点在堆上**分散分布**，CPU 缓存命中率差。
- ArrayList 连续内存，**遍历时局部性好、快得多**。
- 而且 ArrayList 尾部追加也是 O (1)（均摊）。
- 所以除非频繁在**头部 / 中间**插入删除，否则用 ArrayList。

**Q3 源码（30%）**

追问：ArrayList 怎么扩容？

- 默认容量 10（第一次 add 才初始化）。
- 扩容 `newCapacity = oldCapacity + (oldCapacity >> 1)`，即 **1.5 倍**。
- 用 `Arrays.copyOf` 拷贝，O (n)。
- 所以**能预估大小就 `new ArrayList<>(size)`**，避免反复扩容。

**项目钩子**

- “批量导出场景预估容量初始化 ArrayList，减少扩容拷贝。”

### 卡 2　HashMap 底层结构　★★★★

**关键词**：数组 + 链表 + 红黑树 / 桶 / 树化

**串线**：主线第 ②③ 环「怎么定位 / 冲突怎么办」

**Q1 定义（20%）**

- JDK8 的 HashMap 是 **数组 + 链表 + 红黑树**。
- 数组每个位置叫**桶（bucket）**。
- 冲突少用链表，冲突多用红黑树。

**Q2 场景（50%）**

面试官问：什么时候链表转红黑树？

- 链表长度 **≥ 8** 且数组容量 **≥ 64** 才树化。
- 容量不足 64 时优先**扩容**而不是树化。
- 树节点数 **≤ 6** 时退化回链表。
- 阈值 8/6 是为了平衡 “树化开销” 和 “查询效率”。

**Q3 源码（30%）**

追问：为什么阈值是 8？

- 源码注释给的依据是**泊松分布**：链表长度到 8 的概率约 **0.00000006**。
- 正常情况下几乎不会树化。
- 树化本身有开销（要建 TreeNode），所以阈值不能太低。

**项目钩子**

- “排查过一次大 key 导致桶内链表过长、查询变慢的问题。”

### 卡 3　HashMap put 流程　★★★★

**关键词**：hash 扰动 / 定位 / 冲突处理 / 树化

**串线**：主线第 ②③ 环

**Q1 定义（20%）**

- 先算 hash（扰动），再定位桶。
- 桶空就放，桶非空就比 key、冲突则挂链表 / 树。

**Q2 场景（50%）**

面试官问：put 的完整流程是什么？

- ① 算 `hash = h ^ (h >>> 16)`（**高 16 位异或低 16 位**，让高位也参与定位）。
- ② `(n - 1) & hash` 定位桶下标。
- ③ 桶为空，直接放新节点。
- ④ 桶非空：比 key（先 `==` 再 `equals`），相同就覆盖 value。
- ⑤ 不同就挂到链表尾部，长度到 8 且容量 ≥ 64 则树化。
- ⑥ 最后判断是否需要扩容。

**Q3 源码（30%）**

追问：为什么要做 hash 扰动？

- 数组长度通常很小，`(n-1) & hash` 只用到 hash 的**低位**。
- 如果 hash 低位分布差，冲突会很多。
- `h ^ (h >>> 16)` 把**高位混进低位**，让分布更均匀。
- 这是 “用一次异或换更少冲突” 的设计取舍。

**项目钩子**

- “自定义对象做 key 时确保 hashCode 分布均匀。”

### 卡 4　HashMap 容量为什么是 2 的幂　★★★★

**关键词**：位运算 / 取模 / 高低位拆分

**串线**：主线第 ④ 环「扩容怎么搬」

**Q1 定义（20%）**

- 容量必须是 2 的幂，默认 16。
- 这样 `(n - 1) & hash` 才等价于 `hash % n`，且更快。

**Q2 场景（50%）**

面试官问：为什么不用 `hash % n`？

- `%` 是除法，CPU 开销比位运算大。
- 当 n 是 2 的幂时，`(n-1) & hash` 和 `hash % n` **结果完全一样**。
- 所以用位运算替代取模，**又快又对**。
- 这也是扩容时用 `Integer.highestOneBit` 把容量拉到 2 的幂的原因。

**Q3 源码（30%）**

追问：扩容时怎么搬数据？

- JDK8 **不需要重新算 hash**。
- 用 `hash & oldCap` 判断：结果为 0 留在原位置，不为 0 移到 “原位 + oldCap”。
- 这叫**高低位拆分**，一次遍历就把数据分到两个位置。
- 比 JDK7 的 rehash 更高效。

**项目钩子**

- “初始化 HashMap 时用 `new HashMap<>(expectedSize / 0.75 + 1)` 避免扩容。”

### 卡 5　HashMap 扩容与 JDK7 死循环　★★★★

**关键词**：负载因子 / 头插法 / 并发死循环

**串线**：主线第 ④ 环

**Q1 定义（20%）**

- 默认负载因子 **0.75**，元素数超过 `容量 × 0.75` 就扩容为 **2 倍**。
- JDK7 扩容用**头插法**，JDK8 改成**尾插法**。

**Q2 场景（50%）**

面试官问：JDK7 的 HashMap 为什么会死循环？

- 多线程同时扩容，头插法会**把链表顺序反转**。
- 两个线程交叉执行，可能形成**环形链表**。
- 之后 get 遍历时死循环，CPU 打满。
- JDK8 改尾插法解决了死循环，但**仍然线程不安全**（会丢数据）。

**Q3 源码（30%）**

追问：负载因子为什么是 0.75？

- 太大：冲突多，查询慢。
- 太小：空间浪费，扩容频繁。
- 0.75 是**空间和时间的折中**，源码注释里有泊松分布的推导。

**项目钩子**

- “并发场景一律用 ConcurrentHashMap，不用 HashMap。”

### 卡 6　String 的 hashCode 为什么用 31　★★★

**关键词**：奇素数 / 移位优化 / 分布性

**串线**：主线第 ② 环「怎么定位」（hash 的源头）

**Q1 定义（20%）**

- String 的 hashCode 是 `h = 31 * h + char[i]`。
- 31 是**奇素数**。

**Q2 场景（50%）**

面试官问：为什么偏偏是 31？

- 素数能让 hash 分布更均匀，减少冲突。
- 31 是**奇数**，避免乘法溢出丢信息。
- `31 * i` 可以被 JIT 优化成 `(i << 5) - i`，**移位比乘法快**。
- 31 不大不小，冲突和溢出 balance 合适。

**Q3 源码（30%）**

追问：“abc” 的 hashCode 怎么算？

- `h = 31 * (31 * 31 + 'a')...` 等价于 `'a'*31² + 'b'*31 + 'c'`。
- 本质是**多项式滚动哈希**。
- 这也是为什么 hashCode 可能为负数、可能冲突。

**项目钩子**

- “做字符串分片 / 一致性哈希时用同样思路。”

### 卡 7　TreeMap / 红黑树　★★★

**关键词**：有序 / 红黑树 / O (logn) / Comparable

**串线**：主线第 ⑤ 环「有序怎么办」

**Q1 定义（20%）**

- TreeMap 底层是**红黑树**，key 天然有序。
- 操作都是 O (logn)。
- key 必须实现 `Comparable` 或传 `Comparator`。

**Q2 场景（50%）**

面试官问：什么时候用 TreeMap？

- 需要**按 key 排序**遍历。
- 需要**范围查询**（subMap、headMap、tailMap）。
- 需要找**最近的上 / 下界**（floorKey、ceilingKey）。
- 普通 key-value 查找用 HashMap 更快。

**Q3 源码（30%）**

追问：红黑树的五个性质是什么？

- 节点非红即黑。
- 根节点是黑。
- 叶子（NIL）是黑。
- 红节点的子节点必须是黑（不能连续红）。
- 任一节点到叶子的路径上黑节点数相同。
- 这五条保证树**近似平衡**，高度不超过 2log (n+1)。

**项目钩子**

- “做价格区间查询 / 排行榜用 TreeMap 的范围查询。”

### 卡 8　ConcurrentHashMap　★★★★

**关键词**：分段锁 / CAS + synchronized /size 统计

**串线**：主线第 ⑥ 环「并发怎么安全」

**Q1 定义（20%）**

- JDK7 用**分段锁 Segment**（继承 ReentrantLock），锁一段。
- JDK8 改成 **CAS + synchronized 锁单个桶**，粒度更细。

**Q2 场景（50%）**

面试官问：JDK8 为什么放弃分段锁？

- 分段锁粒度还是偏大（一段多个桶）。
- JDK8 直接**锁单个桶的头节点**，并发度更高。
- 空桶插入用 **CAS 无锁**，只有冲突才 synchronized。
- 同时 JDK8 也保留了红黑树优化。

**Q3 源码（30%）**

追问：size 是怎么统计的？为什么不是强一致？

- 用 `baseCount` + `CounterCell[]` 分散计数（类似 LongAdder）。
- 多线程各自累加到不同 cell，减少竞争。
- `size()` 是**弱一致**的，并发时可能不准。
- 这是为了性能牺牲强一致性的设计取舍。

**项目钩子**

- “本地缓存用 ConcurrentHashMap，注意 size 不做强一致用途。”

### 卡 9　fail-fast /modCount　★★★

**关键词**：modCount / expectedModCount / ConcurrentModificationException

**串线**：主线第 ⑦ 环「遍历怎么防篡改」

**Q1 定义（20%）**

- 集合内部维护 `modCount`，每次结构性修改 +1。
- 迭代器创建时记下 `expectedModCount`。
- 遍历时发现两者不一致 → 抛 `ConcurrentModificationException`。

**Q2 场景（50%）**

面试官问：为什么遍历时 remove 会报错？怎么正确删除？

- `for-each` 底层是迭代器，`list.remove()` 改的是 modCount。
- 迭代器没同步自己的 expectedModCount，下次 next 就校验失败。
- 正确做法：用 **`iterator.remove()`**（它会同步 modCount）。
- 或者用 `removeIf`。

**Q3 源码（30%）**

追问：fail-fast 和 fail-safe 区别？

- fail-fast：直接抛异常（ArrayList、HashMap）。
- fail-safe：遍历副本，不抛异常但可能读到旧数据（CopyOnWriteArrayList、ConcurrentHashMap）。
- 取舍：**要么快速失败，要么牺牲一致性**。

**项目钩子**

- “批量删除用 removeIf，避免迭代器异常。”
