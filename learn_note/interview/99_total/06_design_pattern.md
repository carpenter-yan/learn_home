## 设计模式・6 张实战卡（社招高频版）

### 主线：一段代码怎么被组织得可扩展

```
① 只要一个实例      → 单例 DCL + volatile          （卡 1）
② 创建逻辑收口      → 工厂三兄弟                    （卡 2）
③ 不改原类加能力    → 代理 JDK vs CGLIB            （卡 3）
④ 骨架固定步骤可变  → 模板方法 + 钩子               （卡 4）
⑤ 请求要逐层过滤    → 责任链 Filter / Pipeline      （卡 5）
⑥ 行为按场景切换    → 策略替代 if-else              （卡 6）
```

**开场话术（背下来，30 秒）：**

- 设计模式不是背 23 个名字，是回答 “**这段代码为什么要这么拆**”。
- 社招只考 6 个，但这 6 个都要求说出**它在 JDK 或 Spring 里的具体落地**。
- 顺序看：**先造出来（单例、工厂）→ 再增强它（代理）→ 再组织流程（模板、责任链）→ 最后应对变化（策略）**。

**6 个模式一句话定位：**

表格

| 卡 | 模式 | 一句话 | 典型落地 |
| --- | --- | --- | --- |
| 1 | 单例 | 全局只造一个 | `Runtime` / Spring 单例 Bean |
| 2 | 工厂 | 把 new 收口到一处 | `BeanFactory` |
| 3 | 代理 | 不改原类，方法前后加逻辑 | Spring AOP |
| 4 | 模板方法 | 骨架固定，步骤可变 | `JdbcTemplate` |
| 5 | 责任链 | 请求沿链走，逐层决定 | Tomcat Filter / Netty Pipeline |
| 6 | 策略 | 行为抽出来，运行时选 | `Comparator` |

---

## 卡 1　单例（DCL + volatile）　★★★★★

**关键词**：DCL /volatile 半初始化 / 静态内部类 / 枚举

**串线**：主线第 ① 环「只要一个实例」

**Q1 定义（20%）**

- 单例保证全局**只有一个实例**，并提供统一访问点。
- DCL 是 **Double-Checked Locking**，双重检查锁定。
- 两个 `if`：**锁外一次**（性能优化）、**锁内一次**（防重复创建）。

**Q2 场景（50%）**

面试官问：单例怎么写？为什么必须加 volatile？

- 经典写法：`private static volatile 实例`，加懒加载。
- **volatile 不是可选项**：去掉它就可能拿到**半初始化对象**。
- 更推荐两种替代：**静态内部类**、**枚举**。
- 静态内部类：类加载机制保证线程安全，**无锁、懒加载**。
- 枚举：`Effective Java` 推荐，**天然防反射、防反序列化**。

**Q3 源码（30%）**

追问：为什么 `new` 会出问题？

- `new` 分三步：**分配内存 → 初始化 → 引用赋值**。
- 第 2、3 步没有数据依赖，**可以被重排成 1 → 3 → 2**。
- 别的线程此时看到 `instance != null`，但**字段全是默认值**。
- `volatile` 禁的正是 “**跨越 volatile 访问的重排**”，不是全禁。
- 补充：JDK5 之前这个 bug 修不好，JSR-133 修正后才可用。

**项目钩子**

- “配置中心、连接池、线程池都是单例，统一用静态内部类实现。”

## 卡 2　工厂（三种）　★★★★

**关键词**：简单工厂 / 工厂方法 / 抽象工厂 / 收口

**串线**：主线第 ② 环「创建逻辑收口」

**Q1 定义（20%）**

- 工厂的本质是**把 `new` 收口到一处**，调用方只说 “我要什么”。
- 简单工厂：一个类，`if-else` 判断类型，**返回不同实现**。
- 工厂方法：每种产品配一个工厂，**扩展时只加新工厂，不改旧的**。
- 抽象工厂：一个工厂**生产一族产品**（如 “小米工厂出手机 + 耳机”）。

**Q2 场景（50%）**

面试官问：这三种到底怎么选？

- 简单工厂**违反开闭原则**（加产品要改 if），但**代码最少**。
- 工厂方法**符合开闭**，代价是**类数量翻倍**。
- 抽象工厂用于**产品族**，比如 “同一品牌的一套配件”。
- 判据：**产品少且稳定 → 简单工厂；产品常增 → 工厂方法；有产品族 → 抽象工厂**。

**Q3 源码（30%）**

追问：Spring 的 BeanFactory 算哪种？

- `BeanFactory.getBean()` 按名字返回实例，**本质是 “简单工厂 + 反射”**。
- `DefaultListableBeanFactory` 没有为每个 Bean 建一个工厂类。
- 所以**Spring 并没有严格套用工厂方法模式**，它是**用容器 + 反射取代了工厂类**。
- `FactoryBean` 才是更接近 “工厂方法” 的东西 ——**它自己决定怎么创建 Bean**。

**项目钩子**

- “多支付渠道、多消息类型，都靠一个工厂按类型返回具体实现。”

## 卡 3　代理（静态 / JDK 动态 / CGLIB）　★★★★★

**关键词**：静态代理 / JDK Proxy / CGLIB / ASM / Spring AOP

**串线**：主线第 ③ 环「不改原类加能力」

**Q1 定义（20%）**

- 代理就是**在不改目标类的前提下，在方法前后加逻辑**。
- 静态代理：**手写一个代理类**，和原类实现同一接口。
- JDK 动态代理：运行时**生成接口的实现类**，用 `InvocationHandler`。
- CGLIB：运行时**生成目标类的子类**，所以**目标类不能是 final**。

**Q2 场景（50%）**

面试官问：Spring AOP 到底用哪个？

- **有接口 → JDK 动态代理；无接口 → CGLIB。**
- Spring Boot 2.x 起**默认统一用 CGLIB**（`proxyTargetClass=true`）。
- 三种区别的核心：**JDK 只能代理接口，CGLIB 可以代理类**。
- 代价：CGLIB 要生成子类，**不能代理 final 类和 final 方法**。

**Q3 源码（30%）**

追问：JDK 动态代理的底层是什么？

- 入口是 `Proxy.newProxyInstance(loader, interfaces, handler)`。
- 它在运行时**生成一个 `$Proxy0` 类**，实现你传的接口。
- 所有方法调用**转交给 `InvocationHandler.invoke()`**。
- 为什么只能代理接口：**它是 “实现接口”，不是 “继承类”**。
- CGLIB 走 ASM 直接改字节码**生成子类**，所以能代理类。

**项目钩子**

- “日志、鉴权、事务切面都是代理，Spring AOP 帮我们自动织入。”

## 卡 4　模板方法　★★★★

**关键词**：骨架 / 钩子方法 /final/ 好莱坞原则

**串线**：主线第 ④ 环「骨架固定步骤可变」

**Q1 定义（20%）**

- 父类定义**流程骨架**，把可变的那几步留成**抽象方法或钩子**。
- 模板方法本身用 **`final` 修饰**，防止子类改流程。
- 钩子方法（hook）是**空实现**，子类想干预就覆盖，不想就不动。
- 别叫它 “好莱坞原则”—— 记成 “**父类定流程，子类填内容**” 更直接。

**Q2 场景（50%）**

面试官问：你项目里哪里用过？

- `JdbcTemplate.execute()`：**固定的 “拿连接→执行→释放” 骨架**，你只填 SQL 和回调。
- Spring 的 `AbstractApplicationContext.refresh()`：**固定 refresh 流程**，子类只覆盖个别步骤。
- `ThreadPoolExecutor` 的 `beforeExecute/afterExecute` 就是**钩子方法**。
- 判据：**流程多步且顺序固定、每步实现因业务而异**，就是它。

**Q3 源码（30%）**

追问：为什么模板方法要 `final`？

- 因为一旦允许子类覆盖，**骨架就被破坏，模式失效**。
- 另一个细节：`JdbcTemplate` 里真正的骨架方法**调用了抽象或回调**，不是自己写死逻辑。
- **区别于 “简单继承”**：模板方法的特征是**父类主动控制流程**，子类是被动填空。

**项目钩子**

- “任务编排、审批流、数据同步都是固定骨架 + 可变步骤，用模板方法收口。”

## 卡 5　责任链　★★★★

**关键词**：Handler /next/ Filter / Pipeline / 递归

**串线**：主线第 ⑤ 环「请求逐层过滤」

**Q1 定义（20%）**

- 请求沿链传递，**每个节点决定 “处理” 或 “交给下一个”**。
- 关键点：**链是在启动时装配好的，运行时不改结构**。
- 与装饰器的区别：责任链**可能中途终止**，装饰器**一定全走完**。

**Q2 场景（50%）**

面试官问：哪里见过它？

- **Servlet Filter**：`FilterChain.doFilter()`，一层套一层。
- **Spring MVC Interceptor**：`HandlerExecutionChain` 持有拦截器数组。
- **Netty `ChannelPipeline`**：`InboundHandler` / `OutboundHandler` 双向链。
- **Sentinel / 网关的规则链**：限流 → 鉴权 → 参数校验 → 路由。

**Q3 源码（30%）**

追问：Servlet 的 Filter 链怎么串起来的？

- `ApplicationFilterChain` 内部维护 `filters[]` 和 `pos`。
- `doFilter()` 里**递归式推进**：处理完当前，`pos++` 后调下一个。
- **本质是数组 + 游标**，不是链表 —— 但**效果就是责任链**。
- Netty 则是**真正的双向链表**（`prev/next`），支持入站出站两个方向。

**项目钩子**

- “参数校验、风控、灰度都做成链，加规则不用改原有代码。”

## 卡 6　策略　★★★★

**关键词**：Strategy / Context / 替代 if-else / 无状态

**串线**：主线第 ⑥ 环「行为按场景切换」

**Q1 定义（20%）**

- 把 “**怎么做**” 抽成独立对象，运行时选一个塞进去。
- 典型结构：`Context` 持有 `Strategy`，调用它的方法。
- 核心价值：**把 if-else 分支拆成可独立扩展的类**。
- 判据：**分支超过 3 个、且每个分支逻辑不短**，就该考虑它。

**Q2 场景（50%）**

面试官问：策略和简单工厂、状态模式怎么区分？

- **策略 vs 工厂**：工厂解决 “**怎么创建**”，策略解决 “**怎么执行**”。
- **策略 vs 状态**：策略由**外部选**，状态由**对象内部自动流转**。
- **策略 vs if-else**：分支少就用 if，**多了才值得抽**。
- 常见落地：支付方式、计费规则、排序比较器、限流算法。

**Q3 源码（30%）**

追问：JDK 里哪里是策略？

- `Comparator` 是最典型的策略 ——**排序算法不动，比较逻辑你换**。
- `ThreadPoolExecutor` 的四种**拒绝策略**（Abort / CallerRuns / Discard / DiscardOldest）。
- Spring 的 `InstantiationStrategy`：**决定 Bean 用哪种方式实例化**。
- 注意：**策略对象应当无状态**，否则并发下要小心。

**项目钩子**

- “多租户计费规则、多种导出格式，都抽成策略，配置化切换。”
