## Spring Cloud / Alibaba・6 张实战卡（2026 主流版）

### 主线：服务拆开之后，六个问题怎么解

```
① 服务怎么互相找到   → Nacos 注册中心              （卡 1）
② 服务之间怎么调用   → OpenFeign + LoadBalancer    （卡 2）
③ 配置怎么集中管     → Nacos 配置中心 + 动态刷新    （卡 3）
④ 流量怎么控制       → Sentinel 限流熔断降级        （卡 4）★
⑤ 跨服务事务怎么保证 → Seata 四种模式               （卡 5）★
⑥ 入口怎么统一收口   → Gateway 网关                 （卡 6）
```

**开场话术（背下来，30 秒）：**

- Spring Cloud 的题，本质是 “**服务拆开之后，六个问题怎么解决**”。
- **现在的标准答案是 Alibaba 套件**：Nacos + OpenFeign + Sentinel + Seata + Gateway。
- **Ribbon、Hystrix、Zuul、Eureka 都已经淘汰**，面试还在说它们直接扣分。
- 这块只讲 “**组件怎么用、参数怎么调、坑在哪**”，原理留给分布式理论那块。

**已淘汰 vs 现行（这张对比必须先建立）：**

表格

| 已淘汰 | 现在用什么 |
| --- | --- |
| Eureka / Config Server | **Nacos**（二合一） |
| Ribbon | **Spring Cloud LoadBalancer** |
| Hystrix | **Sentinel** |
| Zuul | **Spring Cloud Gateway** |

## 卡 1　Nacos 注册中心　★★★★

**关键词**：心跳 / 临时实例 / AP 与 CP / Distro / Raft

**串线**：主线第 ① 环「服务怎么互相找到」

**Q1 定义（20%）**

- Nacos 是**注册中心 + 配置中心的二合一**，这是它替代 Eureka + Config 的根本原因。
- 注册中心存的是 “**服务名 → 实例地址列表**” 的映射。
- 服务启动时注册，运行中靠**心跳保活**，下线或心跳超时被剔除。

**Q2 场景（50%）**

面试官问：Nacos 和 Eureka 差别在哪？

- **Eureka 只做注册中心，Nacos 能做配置中心**，一套组件解决两件事。
- **Eureka 只有 AP，Nacos 支持 AP 和 CP 两种模式**。
- **Eureka 2.x 已停止维护**，生态基本转向 Nacos。
- 关键参数：**心跳 5s 一次，15s 未收到标记不健康，30s 剔除实例**。

**Q3 源码（30%）**

追问：AP 和 CP 怎么选？临时实例和持久实例什么关系？

- **临时实例（默认）**：靠心跳，走 **AP（Distro 协议）**，实例下线自动摘除。
- **持久实例**：不靠心跳，走 **CP（Raft 协议）**，适合数据库这类要精确的。
- 所以口诀：**“临时实例配 AP，持久实例配 CP”**。
- 部署注意：**集群至少 3 节点**，否则 Raft 选不出主。

**项目钩子**

- “从 Eureka 迁到 Nacos，注册和配置统一管理，运维成本直接减半。”

## 卡 2　OpenFeign + 负载均衡　★★★★

**关键词**：`@FeignClient` / 动态代理 / `LoadBalancer` / 超时重试

**串线**：主线第 ② 环「服务之间怎么调用」

**Q1 定义（20%）**

- OpenFeign 是**声明式 HTTP 客户端**：写个接口加注解，**像调本地方法一样调远程**。
- 底层靠**动态代理**生成实现，真正发 HTTP 请求。
- 配合 **Spring Cloud LoadBalancer** 做客户端负载均衡（**Ribbon 已被移除**）。

**Q2 场景（50%）**

面试官问：Feign 和 RestTemplate 什么区别？

- `RestTemplate` 要**手拼 URL、手动序列化**，代码又长又重复。
- Feign **声明式**，接口即契约，**复用 Spring MVC 注解**。
- 关键配置：**超时和重试必须显式设，默认超时短得离谱**（连接 10s、读 60s，容易误判）。
- 注意：**Feign 默认不开启重试**，开了要小心幂等。

**Q3 源码（30%）**

追问：Feign 的代理是怎么生成的？

- `@FeignClient` 被 `FeignClientFactoryBean` 处理，**生成 `FactoryBean` 注册进容器**。
- `getObject()` 时用 **`ReflectiveFeign.newInstance()` 造 JDK 动态代理**。
- 方法调用被 `InvocationHandler` 拦截 → **拼请求模板 → 走 LoadBalancer 选实例 → 发 HTTP**。
- 版本细节：**Spring Cloud 2022 起配置前缀改成 `spring.cloud.openfeign.*`**，老前缀失效。

**项目钩子**

- “Feign 超时没配，下游慢接口把上游线程打满，后来统一设了连接 2s、读 5s。”

## 卡 3　Nacos 配置中心　★★★★

**关键词**：namespace / group / dataId / `@RefreshScope` / 长轮询

**串线**：主线第 ③ 环「配置怎么集中管」

**Q1 定义（20%）**

- Nacos 配置中心把配置集中到服务端，**客户端启动拉取，运行中监听变更**。
- 三层隔离模型：**namespace（环境）→ group（项目）→ dataId（文件）**。
- 支持**动态刷新**，改配置不用重启。

**Q2 场景（50%）**

面试官问：怎么做到不重启就生效？

- 加 **`@RefreshScope`** 的 Bean 会在配置变更时**被销毁重建**。
- **`@ConfigurationProperties` 也支持刷新**，且比 `@RefreshScope` 更轻。
- 注意坑：**`@RefreshScope` 会重建 Bean，如果有状态或连接池，要小心副作用**。
- 静态字段、`@Value` 注入到非 `@RefreshScope` 的类里，**刷新生效不了**。

**Q3 源码（30%）**

追问：动态刷新底层靠什么？

- **客户端发起长轮询**，默认 30s 一轮。
- 服务端用 `LongPollingService` **把请求 hold 住约 29.5s**，有变更立即返回。
- 客户端收到变更 → 发布 `RefreshEvent` → **`ContextRefresher.refresh()`** 重建 Bean。
- 这个设计的好处：**几乎实时，又不用维持长连接**。

**项目钩子**

- “灰度开关放 Nacos，改完秒级生效，不用发版。”

## 卡 4　Sentinel 流量治理　★★★★★

**关键词**：流控 / 熔断降级 / 滑动窗口 / 规则持久化

**串线**：主线第 ④ 环「流量怎么控制」

**Q1 定义（20%）**

- Sentinel 是阿里开源的**流量治理组件**，替代 Hystrix。
- 两大能力：**流控（限流）** 和 **熔断降级**。
- 核心数据结构是**滑动窗口**，统计 QPS、RT、异常数。

**Q2 场景（50%）**

面试官问：限流和熔断到底有什么区别？

- **限流是 “保护自己”**：进来的流量太多，主动拒绝一部分。
- **熔断是 “保护调用方”**：下游挂了，别再傻等，快速失败。
- 熔断三态：**CLOSED（正常）→ OPEN（熔断）→ HALF_OPEN（放行探测）**。
- 熔断策略三种：**慢调用比例、异常比例、异常数**。

**Q3 源码（30%）**

追问：滑动窗口怎么实现的？规则怎么持久化？

- 底层是 **`LeapArray` 环形数组**，默认 1s 窗口分成 **2 个 500ms 格子**。
- 每个格子是 `Bucket`，**统计成功数、异常数、RT**。
- 流控模式三种：**直接、关联、链路**；流控效果三种：**快速失败、Warm Up、匀速排队**。
- **最重要的坑：规则默认只存内存，重启就没了**。
- 持久化三选：**原始模式（丢）、Pull（本地文件）、Push（推 Nacos，推荐）**。

**项目钩子**

- “大促前给核心接口配了 QPS 限流 + 熔断，规则持久化到 Nacos，避免重启丢规则。”

## 卡 5　Seata 分布式事务　★★★★★

**关键词**：TC / TM / RM / AT / TCC /undo_log/ 全局锁

**串线**：主线第 ⑤ 环「跨服务事务怎么保证」

**Q1 定义（20%）**

- Seata 是阿里开源的**分布式事务解决方案**，解决 “**跨服务、跨库的一致性问题**”。
- 三个角色：**TC 事务协调者（独立部署）、TM 事务管理器（发起方）、RM 资源管理器（参与方）**。
- 业务入口加 **`@GlobalTransactional`**，就开启一个全局事务。

**Q2 场景（50%）**

面试官问：四种模式怎么选？

- **AT（默认推荐）**：**对业务零侵入**，靠自动生成反向 SQL 回滚。
- **TCC**：要写 Try / Confirm / Cancel 三个方法，**侵入大但控制精细**，适合资金。
- **SAGA**：长流程、每一步配补偿，**适合跨公司、跨异构系统**。
- **XA**：强一致但性能差，**只在强一致刚需、量小的场景用**。
- 一句话：**“默认 AT，资金用 TCC，长流程用 SAGA，强一致用 XA”。**

**Q3 源码（30%）**

追问：AT 模式的原理和坑是什么？

- **阶段一就提交本地事务**，同时把**前置镜像 + 后置镜像写进 `undo_log` 表**。
- 阶段二提交：**直接删 `undo_log`**；阶段二回滚：**用前置镜像生成反向 SQL 执行**。
- 回滚前会**校验后置镜像和当前数据是否一致**，防止脏写。
- 关键机制：**全局锁**，保证同一行数据不被两个全局事务同时改。
- 坑：**热点行会因全局锁冲突而变慢**；**必须建 `undo_log` 表**；**数据库支持有限**（MySQL / Oracle / PG 等）。

**项目钩子**

- “跨订单和库存的扣减用 AT 模式，热点商品改为 TCC 拆分，避免全局锁打满。”

## 卡 6　Spring Cloud Gateway　★★★★

**关键词**：Route / Predicate / Filter / WebFlux / 非阻塞

**串线**：主线第 ⑥ 环「入口怎么统一收口」

**Q1 定义（20%）**

- Gateway 是 Spring Cloud 官方网关，**基于 WebFlux + Reactor Netty，全异步非阻塞**。
- 三个核心概念：**Route（路由）、Predicate（断言）、Filter（过滤器）**。
- 一条路由 = **id + uri + 一组断言 + 一组过滤器**。

**Q2 场景（50%）**

面试官问：和 Zuul 比优势在哪？

- **Zuul 1.x 是阻塞式 Servlet，一个请求占一个线程**，高并发下线程耗尽。
- **Gateway 基于 Netty，少量线程处理大量请求**，吞吐高一个量级。
- 常见用法：**统一鉴权、灰度路由、限流、日志、跨域**。
- **最大的坑：千万不要在 Gateway 里写阻塞代码**（JDBC 查询、同步 HTTP），**会把整个网关拖垮**。

**Q3 源码（30%）**

追问：过滤器怎么分？顺序怎么定？

- 两类：**`GatewayFilter`（挂在某条路由上）** 和 **`GlobalFilter`（全局生效）**。
- 排序靠 **`Ordered` 接口或 `@Order`**，**值越小越先执行**。
- 执行链是**“前置逻辑正序、后置逻辑逆序”**—— 和 Filter 一样是洋葱模型。
- 路由匹配在 **`RoutePredicateHandlerMapping`** 里完成。

**项目钩子**

- “鉴权、灰度、限流都收在网关，业务服务不用重复实现。”
