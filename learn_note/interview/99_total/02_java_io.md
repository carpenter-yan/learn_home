## 卡 1　BIO / NIO / AIO 区别　★★★★

**关键词**：同步阻塞 / 同步非阻塞 / 异步 / 线程模型 

**串线**：主线第 ① 环「连接怎么接进来」

**Q1 定义（20%）**

- BIO 同步阻塞，一个连接一个线程，读写全程阻塞。
- NIO 同步非阻塞，靠 Selector 多路复用，一个线程管多连接。
- AIO 异步非阻塞，发起 IO 立即返回，内核读写完再回调通知。

**Q2 场景（50%）**

面试官问：AIO 为什么现实里用得少？

- Linux 内核**没有真正的异步 socket IO**。
- `libaio` 只支持文件，不支持 socket。
- JDK 的 AIO 在 Linux 上其实是**线程池 + epoll 模拟**的。
- Netty 也不用 AIO，生态和成熟度都在 NIO。
- 再加上异步回调编程复杂，所以现实中 AIO 很少见。

**Q3 源码（30%）**

追问：同步 / 异步和阻塞 / 非阻塞到底怎么区分？

- **阻塞 vs 非阻塞**：看调用是否立即返回。
- **同步 vs 异步**：看数据读写由谁完成。
- 两个维度是**正交**的，可以组合。
- BIO = 同步阻塞，NIO = 同步非阻塞，AIO = 异步非阻塞。
- 对应设计模式：NIO 是 **Reactor（就绪通知）**，AIO 是 **Proactor（完成通知）**。

**项目钩子**

- “做长连接 / 网关时用 Netty（基于 NIO），而不是 AIO。”

## 卡 2　select /poll/epoll 区别　★★★★

**关键词**：fd 上限 / O (n) 轮询 / 事件回调 / O (1)

**串线**：主线第 ② 环「内核怎么等数据」

**Q1 定义（20%）**

- select：fd 上限 1024，O (n) 轮询全部 fd。
- poll：没有上限，但仍是 O (n) 轮询。
- epoll：内核事件表 + 回调，O (1)，无上限。

**Q2 场景（50%）**

面试官问：epoll 为什么比 select 快？

- select/poll 每次都要**把全部 fd 拷给内核、再遍历一遍**。
- epoll 把 fd 存在内核的**红黑树**里，只维护一个**就绪链表**。
- 有事件时内核**回调**把就绪 fd 挂到链表上。
- 所以只处理就绪的 fd，O (1) 拿到，fd 越多优势越大。
- Netty、Redis、Nginx 底层都用 epoll。

**Q3 源码（30%）**

追问：epoll 底层三个核心操作是什么？

- `epoll_create`：创建 epoll 实例（红黑树 + 就绪链表）。
- `epoll_ctl`：增删改要监听的 fd。
- `epoll_wait`：等待就绪事件并返回。
- 关键优化是**不需要每次把全部 fd 从用户态拷到内核态**。

**项目钩子**

- “做 IM 长连接时，select 的 1024 上限是实际踩过的坑。”

## 卡 3　LT vs ET 触发模式　★★★★

**关键词**：水平触发 / 边缘触发 / 一次读完

**串线**：主线第 ③ 环「就绪了怎么通知」

**Q1 定义（20%）**

- LT 水平触发：只要 fd 就绪，就**反复通知**。
- ET 边缘触发：只在**状态变化时通知一次**。
- LT 简单安全，ET 高效但要求高。

**Q2 场景（50%）**

面试官问：Netty 默认用哪个？为什么？

- Netty 默认用 **LT**，简单可靠、不容易丢事件。
- ET 效率更高，但**必须一次把数据读干净**。
- 因为 ET 只通知一次，没读完的数据下次不会再通知。

**Q3 源码（30%）**

追问：ET 模式为什么必须循环读到 EAGAIN？

- ET 只在 “从无数据变成有数据” 那一刻通知一次。
- 如果只读一次没读完，剩余数据不会再有新通知。
- 所以要在 `while (true)` 里一直读，直到返回 `EAGAIN`（读空了）。
- 这是 ET 模式最容易写错的地方，也是它的性能来源。

**项目钩子**

- “看 Netty 源码时确认过默认是 LT 模式。”

## 卡 4　NIO 三组件　★★★

**关键词**：Channel / Buffer / Selector / 事件驱动

**串线**：主线第 ④ 环「程序怎么组织」

**Q1 定义（20%）**

- Channel：双向读写，不像流只能单向。
- Buffer：数据容器，读写都经过它。
- Selector：多路复用器，监听多个 Channel 的事件并分发。

**Q2 场景（50%）**

面试官问：NIO 为什么一个线程能管多个连接？

- Selector 把多个 Channel 注册上去。
- 线程调 `select()` 等待，**只处理就绪的 Channel**。
- 没就绪的连接完全不占线程，不阻塞。
- 所以线程数不再随连接数线性增长。

**Q3 源码（30%）**

追问：NIO 有哪些坑？Netty 解决了什么？

- 直接内存 `DirectByteBuffer` 减少一次拷贝，但要手动管理回收。
- JDK NIO 有 **epoll 空轮询 bug**：
  某些情况 select 返回 0 却被当成有事件，CPU 打满。
- Netty 的处理：统计空轮询次数，**超过阈值（默认 512）重建 Selector**。
- 这就是 “为什么用 Netty 而不用裸 NIO” 的实打实理由。

**项目钩子**

- “Netty 里 Channel/Buffer/Selector 的实际使用和调优。”

## 卡 5　零拷贝（Zero Copy）　★★★★

**关键词**：4 次拷贝 / DMA / CPU 拷贝 /mmap/sendfile

**串线**：主线第 ⑤ 环「数据怎么少搬几次」

**Q1 定义（20%）**

- 传统 `read + write` 要 **4 次拷贝**（2 次 DMA + 2 次 CPU）。
- 外加 4 次用户态 / 内核态上下文切换。
- 零拷贝就是把这几次**没必要的 CPU 拷贝**省掉。

**Q2 场景（50%）**

面试官问：谁在用零拷贝？

- **Kafka** 发消息用 `sendfile` 零拷贝。
- **Netty** 支持 sendfile 零拷贝。
- 文件服务器、消息推送这类 “读出来就转发” 的场景收益最大。
- 核心收益是**减少 CPU 拷贝和上下文切换**，不是省内存。

**Q3 源码（30%）**

追问：mmap 和 sendfile 有什么区别？

- **mmap**：用户态和内核共享同一块内存映射，
  省掉 “内核→用户” 的一次 CPU 拷贝。
  适合**需要处理数据**的场景（如读进来算一下再发）。
- **sendfile**：内核直接传输，用户态完全不参与，
  省掉 2 次 CPU 拷贝，只剩 2 次 DMA。
  适合**纯转发**（Kafka、文件下载）。
- 严格说 sendfile 还有 2 次 DMA 拷贝，叫 “**零 CPU 拷贝**” 更准确。

**项目钩子**

- “消息推送 / 文件下载场景了解过 sendfile。”

## 卡 6　五种 IO 模型　★★★

**关键词**：阻塞 / 非阻塞 / 多路复用 / 信号驱动 / 异步

**串线**：主线第 ⑥ 环「模型怎么归类」（全景总结）

**Q1 定义（20%）**

- 五种模型：阻塞 IO、非阻塞 IO、IO 多路复用、信号驱动、异步 IO。
- Java 的 BIO 大致对应阻塞，NIO 对应多路复用，AIO 对应异步。

**Q2 场景（50%）**

面试官问：多路复用和异步 IO 的区别？

- 多路复用是**同步**的：内核通知 “就绪了”，**数据你自己读**。
- 异步是内核**帮你读完**，再通知你结果。
- 一句话：多路复用是 “就绪通知”，异步是 “完成通知”。

**Q3 源码（30%）**

追问：Java 有没有 “信号驱动 IO”？

- 没有直接对应。
- Java 没有暴露信号驱动 IO 的 API。
- 所以 Java 实际用的是前三种 + 异步这四种。

**项目钩子**

- “给团队讲过 IO 模型图，用这张图统一过技术口径。”

## 卡 7　Java 原生序列化为什么不推荐　★★★

**关键词**：体积大 / 慢 / 不安全 / 跨语言差

**串线**：主线第 ⑦ 环「数据怎么变成字节」

**Q1 定义（20%）**

- 原生序列化会把**类元信息一起写死**，体积大。
- 反射 + IO，性能慢。
- 反序列化会自动执行 `readObject`，有安全风险。
- 只能 Java 之间用，跨语言差。

**Q2 场景（50%）**

面试官问：那应该用什么替代？

- 跨语言、高性能选 **Protobuf**。
- 通用、可读选 **JSON（Jackson/Gson）**。
- Java 内部 RPC 可用 Hessian。
- 原生序列化基本淘汰。

**Q3 源码（30%）**

追问：原生序列化具体浪费在哪？

- 字节流里写了**类名、serialVersionUID、字段描述**。
- 体积经常比 JSON 还大。
- 反序列化还要**反射创建对象再赋值**。
- 这两点决定了它 “又大又慢”。

**项目钩子**

- “RPC 传输从 Java 原生换 Protobuf 的经历。”

## 卡 8　serialVersionUID　★★★

**关键词**：版本号 / 自动生成 / InvalidClassException

**串线**：主线第 ⑧ 环「版本怎么对齐」

**Q1 定义（20%）**

- 序列化版本号。
- 不写的话，JVM 按类结构**自动生成**一个。
- 类一改（加字段 / 方法），UID 就变。
- 反序列化旧数据抛 `InvalidClassException`。
- 所以要显式声明固定值。

**Q2 场景（50%）**

面试官问：不写会怎样？

- 类结构哪怕微调一下，UID 就变了。
- 老数据反序列化直接失败。
- 写死 UID 才能保证版本兼容演进。
- 改动不兼容时再主动改 UID。

**Q3 源码（30%）**

追问：UID 怎么生成、什么时候该改？

- 用 `serialver` 工具或 IDE 生成。
- 加字段一般可兼容，不用改 UID。
- 改字段类型、删字段属于不兼容变更，要改 UID。

**项目钩子**

- “曾因没写 UID 导致线上缓存反序列化失败。”

## 卡 9　序列化框架选型　★★★

**关键词**：Protobuf / JSON / Hessian / 场景

**串线**：主线第 ⑨ 环「选哪个框架」

**Q1 定义（20%）**

- 跨语言高性能：Protobuf。
- 通用可读：JSON（Jackson/Gson）。
- Java 内部 RPC：Hessian。
- 原生序列化：基本淘汰。

**Q2 场景（50%）**

面试官问：Protobuf 为什么快？

- 二进制编码 + **字段编号**，没有冗余键名。
- 体积小、解析快。
- 代价是**可读性差**，要维护 `.proto` 文件。
- 前后端、跨语言场景优势明显。

**Q3 源码（30%）**

追问：Jackson 和 Fastjson 怎么选？

- Jackson 生态成熟、社区活跃、**安全记录更好**。
- Fastjson 曾多次爆 **autoType 漏洞**。
- 现在企业主流是 Jackson，Fastjson 逐步淘汰。
- 选型要看：性能、跨语言、安全记录、生态。

**项目钩子**

- “项目里做过 Jackson 替换 Fastjson 的安全治理。”

## 卡 10　反序列化安全漏洞　★★★

**关键词**：readObject / RCE / Fastjson autoType

**串线**：主线第 ⑩ 环「怎么防被攻击」

**Q1 定义（20%）**

- Java 反序列化会调用对象的 `readObject`。
- 攻击者可构造**恶意字节流**触发任意代码执行（RCE）。
- Fastjson 曾因 `autoType` 可加载任意类而爆漏洞。

**Q2 场景（50%）**

面试官问：怎么防？

- 禁用 / 限制 `autoType`。
- 用**白名单**限制可反序列化的类。
- 不反序列化**不可信来源**的数据。
- 优先用 JSON/Protobuf，别用 Java 原生。

**Q3 源码（30%）**

追问：Java 原生反序列化 RCE 的原理？

- **gadget chain（利用链）**：
  如 CommonsCollections 这类库，
  反序列化时触发反射调用 `Runtime.exec`。
- Fastjson 的 `autoType`：
  通过 `@type` 指定加载恶意类，实例化时触发利用链。
- 本质都是 “**反序列化等于让数据决定执行什么代码**”。

**项目钩子**

- “安全扫描 / 依赖治理时处理过 fastjson 漏洞。”
