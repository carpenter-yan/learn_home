# 三、Java 虚拟机（JVM）・9 张实战卡（按主线顺序）
## 主线：字节码怎么变成机器码，对象怎么活怎么死

```
① 类怎么加载      → 类加载五步、双亲委派
② 内存怎么分区    → 堆 / 栈 / 元空间
③ 对象怎么创建    → 对象头、指针压缩、TLAB
④ 对象怎么判死    → 可达性分析、GC Roots
⑤ 垃圾怎么收      → GC 算法、分代
⑥ 收集器怎么选    → CMS / G1 / ZGC
⑦ 线上怎么排查    → 参数、OOM、MAT
```

### 卡 1　类加载过程　★★★★

**关键词**：加载 / 验证 / 准备 / 解析 / 初始化

**串线**：主线第 ① 环「类怎么加载」

**Q1 定义（20%）**

- 五个阶段：加载 → 验证 → 准备 → 解析 → 初始化。
- 之后还有使用、卸载。

**Q2 场景（50%）**

面试官问：准备阶段和初始化阶段分别做什么？

- **准备**：给 static 变量分配内存并赋**零值**（0、null、false）。
- static final 常量在**准备阶段就赋值**（因为是编译期常量）。
- **初始化**：执行 `<clinit>()`，即 static 变量赋值和 static 块。
- 顺序：父类先初始化，再子类。

**Q3 源码（30%）**

追问：什么时候触发初始化？

- `new` 实例、访问静态字段 / 方法。
- 反射 `Class.forName`。
- 子类初始化会先初始化父类。
- 作为 main 类启动。
- 注意：**访问 static final 编译期常量不触发初始化**（常量已内联）。

**项目钩子**

- “排查过 static 初始化顺序导致 NPE 的问题。”

### 卡 2　双亲委派　★★★★

**关键词**：Bootstrap / Platform / App / 打破

**串线**：主线第 ① 环

**Q1 定义（20%）**

- 类加载器有层级：Bootstrap → Platform (Extension) → Application → 自定义。
- 收到加载请求，**先委派给父加载器**，父加载不了才自己加载。

**Q2 场景（50%）**

面试官问：为什么要双亲委派？

- 保证**核心类不被篡改**（你自己写的 `java.lang.String` 加载不了）。
- 保证**同一个类只加载一次**（父加载器优先）。
- 本质是 “**安全 + 唯一性**”。

**Q3 源码（30%）**

追问：怎么打破双亲委派？

- **SPI**（JDBC）：父加载器加载的接口要调用子加载器加载的实现，用 `Thread.currentThread().getContextClassLoader()`。
- **Tomcat**：每个 WebApp 有自己的 `WebAppClassLoader`，优先加载自己的类，实现应用隔离。
- **OSGi**：网状委派。

**项目钩子**

- “写过自定义 ClassLoader 做热部署 / 插件隔离。”

### 卡 3　JVM 内存区域　★★★★

**关键词**：堆 / 栈 / 元空间 / 程序计数器

**串线**：主线第 ② 环「内存怎么分区」

**Q1 定义（20%）**

- **线程私有**：程序计数器、虚拟机栈、本地方法栈。
- **线程共享**：堆、方法区（JDK8 用元空间实现，在本地内存）。
- 堆是 GC 主战场，栈随线程生死。

**Q2 场景（50%）**

面试官问：JDK8 为什么用元空间替换永久代？

- 永久代在堆内，大小固定，容易 `PermGen OOM`。
- 元空间用**本地内存**，默认不设上限（受物理内存限制）。
- 类元数据、字符串常量池位置也调整了（StringTable 移到堆）。
- 好处：减少 OOM，回收更灵活。

**Q3 源码（30%）**

追问：栈上会 OOM 吗？会 StackOverflow 吗？

- 栈**不会 OOM**（除非创建大量线程耗尽内存）。
- 栈溢出是 `StackOverflowError`—— 递归太深。
- 堆溢出是 `OutOfMemoryError: Java heap space`。

**项目钩子**

- “线上调 `-Xmx` / `-Xms` 和 `-XX:MaxMetaspaceSize` 控制内存。”

### 卡 4　对象创建与对象头　★★★

**关键词**：Mark Word / Klass Pointer / 指针压缩 / TLAB

**串线**：主线第 ③ 环「对象怎么创建」

**Q1 定义（20%）**

- 对象内存布局：**对象头 + 实例数据 + 对齐填充**。
- 对象头 = Mark Word（哈希、GC 年龄、锁标志）+ Klass Pointer（类型指针）。

**Q2 场景（50%）**

面试官问：对象创建的过程是什么？

- ① 类加载检查。
- ② 分配内存（**指针碰撞**或**空闲列表**）。
- ③ **TLAB**：线程本地分配缓冲，避免分配时加锁。
- ④ 初始化零值。
- ⑤ 设置对象头（Mark Word）。
- ⑥ 执行构造器 `<init>`。

**Q3 源码（30%）**

追问：什么是指针压缩？

- 64 位 JVM 默认开启 `-XX:+UseCompressedOops`。
- 对象引用从 8 字节压到 **4 字节**，节省内存。
- 因为对象地址按 8 字节对齐，低 3 位是 0，可以省掉，用移位还原。
- 堆小于 32G 时才有意义（超过 32G 无法压缩）。

**项目钩子**

- “调过大堆场景下指针压缩失效导致内存暴涨的问题。”

### 卡 5　垃圾判定：可达性分析　★★★★

**关键词**：GC Roots / 引用计数 / 四种引用

**串线**：主线第 ④ 环「对象怎么判死」

**Q1 定义（20%）**

- JVM 用**可达性分析**，不是引用计数。
- 从 **GC Roots** 出发遍历，不可达的对象才可回收。

**Q2 场景（50%）**

面试官问：为什么不用引用计数？

- 引用计数无法解决**循环引用**（A 引用 B，B 引用 A，都回收不掉）。
- 而且每次引用变更都要维护计数，有开销。
- 可达性分析能一次性解决循环引用。

**Q3 源码（30%）**

追问：GC Roots 有哪些？

- 虚拟机栈中局部变量引用的对象。
- 方法区静态变量引用的对象。
- 方法区常量引用的对象。
- JNI（native）引用的对象。
- 活跃的 Thread 对象。

**项目钩子**

- “用 MAT 分析时从 GC Roots 找引用链定位泄漏。”

### 卡 6　GC 算法与分代　★★★★

**关键词**：标记清除 / 复制 / 标记整理 / 分代

**串线**：主线第 ⑤ 环「垃圾怎么收」

**Q1 定义（20%）**

- 标记 - 清除：标记后直接清，有**内存碎片**。
- 复制：把存活对象复制到另一半，无碎片但浪费空间。
- 标记 - 整理：标记后**压缩**，无碎片但移动对象成本高。
- 分代：新生代用复制，老年代用标记清除 / 整理。

**Q2 场景（50%）**

面试官问：为什么新生代用复制算法？

- 新生代对象**朝生夕死**，存活率低。
- 复制算法只需复制少量存活对象，效率高。
- 用 **Eden : Survivor = 8 : 1 : 1**，只浪费 10%。
- 老年代存活率高，复制成本太大，所以用标记 - 整理。

**Q3 源码（30%）**

追问：对象什么时候晋升老年代？

- 年龄达到 **15**（`-XX:MaxTenuringThreshold`，默认 15）。
- **大对象**直接进老年代（`-XX:PretenureSizeThreshold`）。
- **动态年龄判定**：Survivor 中同龄对象超过一半就晋升。
- Survivor 空间不足也会**提前晋升**。

**项目钩子**

- “调 Survivor 比例和晋升阈值优化过 GC 频率。”

### 卡 7　G1 收集器　★★★★

**关键词**：Region / SATB / Mixed GC / 可预测停顿

**串线**：主线第 ⑥ 环「收集器怎么选」

**Q1 定义（20%）**

- G1 把堆分成**大小相等的 Region**（1-32MB），逻辑上仍分新生代 / 老年代。
- 目标是**可预测停顿时间**（`-XX:MaxGCPauseMillis`）。

**Q2 场景（50%）**

面试官问：G1 为什么能控制停顿？

- 维护一个**优先列表**，优先回收 “垃圾最多” 的 Region（Garbage First 得名）。
- 每次只回收部分 Region，用**停顿预测模型**控制在目标时间内。
- 分 **Young GC** 和 **Mixed GC**（回收年轻代 + 部分老年代）。

**Q3 源码（30%）**

追问：G1 用什么解决并发标记的问题？

- **SATB（Snapshot-At-The-Beginning）**：标记开始时拍快照，之后新产生的引用按 “删除时记录” 处理。
- 用**写屏障**记录引用的删除（TAMS 指针）。
- 还有 **Humongous Region** 存放大对象（超过 Region 一半）。

**项目钩子**

- “线上大堆（16G+）用 G1，控制 GC 停顿在 200ms 内。”

### 卡 8　CMS / G1 / ZGC 对比　★★★

**关键词**：并发标记 / 碎片 / 染色指针

**串线**：主线第 ⑥ 环

**Q1 定义（20%）**

- CMS：并发标记清除，**低停顿但有碎片**，JDK14 已移除。
- G1：Region + 可预测停顿，**JDK9 之后默认**。
- ZGC：**染色指针 + 并发整理**，停顿亚毫秒级。

**Q2 场景（50%）**

面试官问：为什么 CMS 被淘汰？

- 有**内存碎片**（标记清除不整理），大对象分配失败会触发 Full GC。
- **并发模式失败**（Concurrent Mode Failure）会退化成串行 Full GC，停顿很长。
- 维护成本高，被 G1 取代。

**Q3 源码（30%）**

追问：ZGC 为什么能做到亚毫秒？

- 用**染色指针**（Colored Pointer）把标记信息存在指针的高位。
- 标记、整理**全并发**执行，只有极短的 STW 阶段。
- 支持**TB 级堆**，停顿不随堆大小增长。
- 代价是吞吐量略低、需要更大内存。

**项目钩子**

- “超大堆 / 低延迟场景考虑 ZGC，普通业务 G1 足够。”

### 卡 9　OOM / 内存泄漏排查　★★★★

**关键词**：jps / jmap / jstack / MAT / Arthas

**串线**：主线第 ⑦ 环「线上怎么排查」

**Q1 定义（20%）**

- 常用工具：`jps`（进程）、`jmap`（堆快照）、`jstack`（线程栈）、`jstat`（GC 统计）、MAT / Arthas。

**Q2 场景（50%）**

面试官问：线上 OOM 了怎么排查？

- ① 先加参数保留现场：`-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/path`。
- ② 用 `jmap -dump` 或自动 dump 拿到堆快照。
- ③ 用 **MAT** 打开，看 **Dominator Tree** 找最大对象。
- ④ 顺引用链找到是谁持有它没释放。
- ⑤ 常见原因：缓存无上限、ThreadLocal 未 remove、集合只增不删、连接未关闭。

**Q3 源码（30%）**

追问：怎么区分内存泄漏和内存溢出？

- **泄漏**：对象该回收但没回收，占用持续增长。
- **溢出**：确实需要的内存超过堆上限。
- 判断方法：看 GC 后老年代占用是否持续上升 —— 不降就是泄漏。
- `jstat -gcutil` 观察老年代占比趋势最直观。

**项目钩子**

- “用 MAT 的 Dominator Tree 定位过一次静态 Map 无限增长导致的 OOM。”
