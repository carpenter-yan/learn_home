## 附卡　基础生态速览（4 合 1）　★★★★

### 主线：一条请求链路上的四个支撑点

```
① 出问题怎么查     → 日志：SLF4J 门面 + Logback 实现   （段 1）
② 数据怎么进出     → 序列化：Jackson                    （段 2）
③ 多节点怎么互斥   → 锁：Redisson 分布式锁              （段 3）
④ 定时任务怎么跑   → 调度：XXL-Job                      （段 4）
```

**开场话术（这四项的定位，30 秒）：**

- 这四项**不是框架，是基础设施**—— 面试通常不会深挖，但答不上来会显得 “没做过生产”。
- 每项只要做到三件事：**说清它解决什么问题、说出它和替代品的区别、说出一个真实的坑**。
- **四段按 “查日志 → 传数据 → 防并发 → 跑定时” 排，刚好是一次线上问题排查的顺序。**

### 段 1　SLF4J + Logback　★★★★

**关键词**：门面模式 / 日志桥接 / `AsyncAppender` / MDC

**串线**：主线第 ① 环「出问题怎么查」

**Q1 定义（20%）**

- **SLF4J 是门面（Facade）**：只定义 API，不实现，项目里所有代码只依赖它。
- **Logback 是实现**：和 SLF4J 同一个人写的，天然适配、性能最好。
- 一句话：**“门面锁死 API，实现随时可换”—— 这就是门面模式。**

**Q2 场景（50%）**

面试官问：项目里为什么同时出现 log4j、slf4j、commons-logging？

- 因为**依赖传递**把别的门面也带进来了，日志会重复打印或不打印。
- 解决靠**桥接包**：`jcl-over-slf4j`、`log4j-over-slf4j` **把老门面转成 SLF4J**。
- 反过来还有 `slf4j-log4j12` 这种**绑定包**——**它决定 SLF4J 最终落到哪个实现**。

**Q3 源码（30%）**

追问：异步日志会不会丢日志？

- `AsyncAppender` 底层是 **`ArrayBlockingQueue`**，默认容量 256。
- **队列满了默认丢弃 WARN 以下的日志**（`discardingThreshold` 默认是队列的 20%）。
- **MDC 底层是 `ThreadLocal<Map>`**—— 这就是线上 TraceId 链路追踪的实现原理。

**项目钩子**

- “统一日志规范 + MDC 注入 TraceId，线上定位问题从半小时缩到五分钟。”

### 段 2　Jackson　★★★★

**关键词**：`ObjectMapper` / `TypeReference` / 泛型擦除 / Fastjson 对比

**串线**：主线第 ② 环「数据怎么进出」

**Q1 定义（20%）**

- **Jackson 是 Spring Boot 默认的 JSON 库**，`spring-boot-starter-web` 自带。
- 核心是 **`ObjectMapper`**，**线程安全，应当做成单例全局复用**。
- 和 Fastjson 的关系：**Jackson 功能全、安全记录好；Fastjson 快但漏洞史长。**

**Q2 场景（50%）**

面试官问：泛型反序列化怎么做？为什么必须写 `{}`？

- 必须用 **`new TypeReference<List<User>>() {}`**，**`{}` 绝对不能省**。
- 因为 `TypeReference` 靠**匿名子类的字节码里保留的泛型签名**来拿真实类型。
- 少写 `{}` 就变成普通对象，**泛型被擦除，只能拿到 `List` 拿不到 `User`**。
- 常用配置：**忽略未知字段、日期不转时间戳、空值处理**，都要在全局统一。

**Q3 源码（30%）**

追问：`ObjectMapper` 能随便 `configure()` 吗？

- **它是线程安全的 “读”，但不是 “并发写安全”**——**运行中改配置是危险操作**。
- 正确做法：**启动时一次性配好，之后只读**。
- 内部有 **`SerializerProvider` / `DeserializerProvider` 缓存**，**所以复用实例比每次 new 快一个量级**。

**项目钩子**

- “统一 `ObjectMapper` 配置，解决了跨服务时间格式不一致的问题。”

### 段 3　Redisson 分布式锁　★★★★★

**关键词**：`RLock` / Hash 重入 / 看门狗 / Lua 解锁 / RedLock

**串线**：主线第 ③ 环「多节点怎么互斥」

**Q1 定义（20%）**

- Redisson 是**基于 Redis 的 Java 客户端**，提供**分布式锁、限流器、分布式集合**。
- 锁的核心是 **`RLock`**，底层是 **Redis Hash**：**key = 锁名，field = 线程标识，value = 重入次数**。
- 一句话：**“用 Hash 存重入计数，这是它比裸 `SETNX` 强的地方。”**

**Q2 场景（50%）**

面试官问：为什么不自己用 `SETNX` 写？

- `SETNX` 三大缺陷：**不支持重入、不会自动续期、解锁可能误删别人的锁**。
- **看门狗（watchdog）**：后台线程**每 10 秒把过期时间续到 30 秒**，业务没跑完锁不会掉。
- **关键细节：只有不指定 `leaseTime` 时才启用看门狗**，指定了就按指定时间过期、不续期。
- **红锁（RedLock）**：多个独立 Redis 节点**过半加锁成功才算成功**，但**争议很大**，生产更推荐**单节点 + 业务幂等**。

**Q3 源码（30%）**

追问：解锁为什么要用 Lua？

- 解锁必须**“判断是我的锁 + 计数减一 + 归零才删” 三步原子执行**。
- 不用 Lua 就是**先 `GET` 再 `DEL`**，中间可能被别人抢走并误删。
- 加锁脚本核心是 **`hincrby` 重入计数 + `pexpire` 设过期 + `hexists` 判重入**。
- 这也是为什么**分布式锁的正确实现几乎都离不开 Lua**。

**项目钩子**

- “秒杀防超卖用 Redisson 锁，配合业务幂等，避免锁失效后的重复扣减。”

### 段 4　XXL-Job　★★★★

**关键词**：调度中心 / 执行器 / 分片广播 / DB 行锁

**串线**：主线第 ④ 环「定时任务怎么跑」

**Q1 定义（20%）**

- XXL-Job 是**国内最常用的分布式任务调度平台**。
- 架构：**调度中心（Admin）统一管理 + 执行器（Executor）注册上来领任务**。
- 一句话：**“调度中心负责决定谁跑，执行器负责真跑。”**

**Q2 场景（50%）**

面试官问：和 Quartz 什么区别？

- **Quartz 是单机库**，集群部署会**同一任务被多台重复执行**，得自己加分布式锁。
- **XXL-Job 自带分布式调度**，**同一时刻只有一个执行器抢到任务**。
- **分片广播**：一个任务广播到所有执行器，各自处理 `id % 分片总数` 那一份 ——**这是它处理大数据的杀手锏**。
- **失败重试**按任务维度配置，重试策略可配。

**Q3 源码（30%）**

追问：怎么保证不重复执行？

- 靠 **DB 行锁**：执行器抢任务时 `select ... for update` 锁住那一行。
- **注册中心靠心跳维护执行器存活**，超时未心跳的摘除。
- 已知问题：**调度中心本身是单点**（多部署也要走同一张表），**任务幂等仍要靠业务保证**。

**项目钩子**

- “数据同步任务用分片广播，千万级数据从 40 分钟压到 6 分钟。”
