## 事务特性？
ACID
- 原子性:一个事务中的操作要么全部成功，要么全部失败。
- 持久性:永久保存在数据库中。
- 一致性:事务前后数据的完整性必须保持一致，总是从一个一致性的状态转换到另一个一致性的状态
- 隔离性:当多个事务同时触发时，不能被其他事务的操作所干扰，多个并发事务之间要相互隔离。
------------------------------------------------------------------------------
## 事务隔离级别？
- 读未提交: 即能够读取到没有被提交的数据
- 读已提交: 即能够读取到那些已经提交的数据
- 可重复读: 可重复读指的是在一个事务内，最开始读到的数据和事务结束前的任意时刻读到的同一批数据都是一致的
- 可串行化: 最高事务隔离级别，不管多少事务，都是依次按序一个一个执行

脏读: 脏读指的是读到了其他事务未提交的数据，未提交意味着这些数据可能会回滚，也就是可能最终不会存到数据库中，也就是不存在的数据。
不可重复读:对比可重复读，不可重复读指的是在同一事务内，不同的时刻读到的同一批数据可能是不一样的。
幻读:幻读是针对数据插入（INSERT）操作来说的。
    假设事务A对某些行的内容作了更改，但是还未提交，此时事务B插入了与事务A更改前的记录相同的记录行，并且在事务A提交之前先提交了，
    而这时，在事务A中查询，会发现好像刚刚的更改对于某些数据未起作用，但其实是事务B刚插入进来的这就叫幻读

## 为什么不要使用长事务?
1. 并发情况下，数据库连接池容易被撑爆
2. 容易造成大量的阻塞和锁超时
   长事务还占用锁资源，也可能拖垮整个库
3. 执行时间长，容易造成主从延迟
4. 回滚所需要的时间比较长
   事务越长整个时间段内的事务也就越多
5. undo log 日志越来越大
   长事务意味着系统里面会存在很老的事务视图。由于这些事务随时可能访问数据库里面的任何数据，
   所以这个事务提交之前，数据库里面它可能用到的回滚记录都必须保留，这就会导致占用大量存储空间。

## 如何实现分布式事务？
分布式事务场景：一次业务横跨多个数据库、多个微服务（订单库、库存库、支付库、财务库），需要保证要么全部成功提交，要么全部回滚，不会出现部分成功、部分失败的单边账。
本地事务只管控单库；跨库必须使用分布式事务。主流分为5套成熟方案，按一致性强度、性能、落地成本划分。
### 一、CAP&BASE前置认知
CAP：分布式系统无法同时满足一致性C、可用性A、分区容错P；网络故障必然发生，P必选。只能在C和A取舍。
BASE：互联网落地理论，基本可用、柔性状态、最终一致。绝大多数订单、结算采用最终一致性，牺牲强一致换高可用。银行转账等金融核心用强一致性。
CAP告诉你「没得选，只能AP」；BASE告诉你「AP该怎么设计、怎么做到最终一致」。
### 二、五大主流分布式事务方案
#### 方案 1：2PC 两阶段提交（强一致性，XA）
执行流程
准备阶段（Prepare）
协调者通知所有参与的数据库/资源：执行SQL、锁定资源，但不提交；所有参与者返回 OK / 失败。只要任意节点失败，全部回滚。
提交阶段（Commit）
所有参与者全部准备成功，协调者下发提交指令，所有节点真正提交；任意节点准备失败，统一发起回滚。
优点 强一致性，全程严格 ACID； MySQL、Redis、MQ 都支持XA协议。
致命缺点 性能极差：Prepare 阶段全程锁资源，长事务严重阻塞；协调者宕机、网络中断会造成阻塞死锁；高并发订单、库存绝对不推荐。
使用场景 传统银行、财务对账内部系统；互联网业务基本不用。
#### 方案 2：TCC（Try-Confirm-Cancel，侵入代码的强最终一致）
把业务手动拆成三段，完全由代码管控，无数据库锁阻塞。
Try 预留资源：检查校验，冻结资源。订单冻结库存、冻结账户余额；数据状态标记为「预留中」。
Confirm 确认提交：全部Try成功，执行业务真正提交，扣减库存、扣钱、正式生成订单。只会正向执行。
Cancel 回滚补偿：任意环节失败，释放冻结资源，解冻库存、恢复余额，撤销单据。只会回滚。
核心规则 三段接口必须保证幂等，防止重复调用错乱；支持空回滚（没执行 Try 也能 Cancel）、防悬挂（Cancel早于Try）。
优点 无数据库长锁，并发性能好；一致性可控，适合资金、库存。
缺点 代码侵入极强，每个业务都要手写三套接口，开发工作量翻倍。
落地场景 高并发库存扣减、支付、业财结算；Seata 框架封装 TCC 降低开发成本。
####方案 3：可靠消息最终一致性（最常用，互联网订单首选）
依靠MQ实现异步最终一致，业界落地最多，适配下单、支付、采购结算。
整体分为5个模块：本地消息表、事务消息、死信队列、定时任务兜底、幂等。
- 标准流程（本地消息表通用方案）
1. 本地事务：执行业务SQL（创建订单） + 插入一条msg_message消息表记录，同库本地事务保证原子性；
2. 独立定时任务轮询消息表，把待发送消息投递MQ；投递成功修改消息状态；投递失败重试；
3. 下游服务消费MQ，执行对应业务（扣库存、财务入账）；消费成功ACK；
4. 消费失败：MQ重试；多次失败进入死信队列，人工排查；
5. 兜底：定时任务定时对账，核对业务表和消息表，补发丢失消息。
- RocketMQ事务消息（不用本地消息表）
1. 发送半消息（对下游不可见）；
2. 执行本地订单事务；
3. 本地成功：提交消息，下游可见；本地失败：回滚消息，下游收不到；
4. 服务宕机：Broker 回查本地事务状态，保证最终落地。
优点 低侵入，不用拆分业务接口；并发高、吞吐大，适配绝大多数订单场景。
缺点 最终一致，有短暂数据不一致（毫秒～秒级），不能接受中间状态的业务不可用。
适配场景 下单、支付回调、采购入库、财务异步对账、大部分业财流转。
#### 方案4：SAGA 模式（长事务、多服务流程，适合复杂业务）
分两类：编排式、编排器式
1. 编排 SAGA（最常用）：每个服务提供正向接口 + 补偿回滚接口。
流程串行执行：A成功→执行B；B失败，反向依次调用B补偿、A补偿，整体回滚。
2. 中心化编排：通过工作流引擎（Camunda、Seata Saga）配置流程，不用硬编码判断。
特点 无资源预留，不需要Try；适合长链路复杂流程：采购全流程、售后退货、多步骤结算。 不需要冻结资源，适配耗时久的业务。
缺点 补偿逻辑复杂，需要梳理全部逆向回滚逻辑；中间状态多。
场景 长链路采购、售后退款、多步骤业财核销。
#### 方案5：最大努力通知（最低成本，适配通知类）
适用：短信、邮件、推送、第三方对账通知，允许最终送达，允许短暂丢失。
1. 本地业务完成；
2. 调用通知接口，失败无限重试；
3. 定时对账兜底；
   不影响核心账务，尽力送达即可。
   绝对不用在订单、扣款等核心链路。
### 三、Seata主流框架落地（面试高频）
Seata一站式封装四种模式：AT、TCC、SAGA、XA，微服务标配。
#### AT模式（无侵入首选，Seata 最火）
自动代理SQL，不用改业务代码，底层是改良版2PC。
一阶段：执行业务 DML，记录undo回滚日志，行锁提交释放；本地事务完成。
二阶段提交：删除undo日志；二阶段回滚：根据undo日志自动回滚数据。
优点 代码零侵入，只加注解@GlobalTransactional，开发最简单。
缺点 一阶段持有行锁到二阶段，跨服务等待会持有锁；高并发热点库存慎用。
### 四、方案选型对照表（订单 / 结算直接照选）

业务场景|推荐方案|原因
--|--|--
普通下单、支付、异步扣库存|可靠消息 MQ|高吞吐、低侵入
秒杀高并发库存、资金扣款|TCC|无长锁，并发高，资金安全
采购履约、售后退货长流程|SAGA|链路长，分步补偿
传统老旧财务系统，必须强一致|XA 2PC|强一致，接受低并发
短信、对账推送|最大努力通知|简单够用
SpringCloud 微服务快速开发|Seata AT|零代码改造

### 五、分布式事务必备兜底三板斧（无论用哪种方案）
所有接口幂等：防重复投递、重复重试造成重复扣款、重复建单；
定时对账：定时任务核对订单、库存、财务流水，不一致自动告警修复；任何框架都可能丢消息，对账是最后防线；
业务状态机：所有单据有明确状态，失败可重入、可回滚。
### 六、高频踩坑
不要用XA做高并发订单，锁等待极易雪崩；
只靠MQ不靠对账：网络丢消息必然出现单边账；
重试没做幂等：重复消费导致多次扣款；
Seata AT适合普通业务，热点商品高并发锁竞争建议改用TCC。
### 七、极简背诵版
XA(2PC) 强一致、性能差；TCC三段手动编码，适合高并发资金库存；
可靠消息最终一致性是互联网订单主流，MQ + 本地消息表 + 对账兜底；
SAGA适合长流程业务；最大努力通知只做推送；
Seata AT无侵入最通用；分布式事务三保障：幂等、重试、定时对账；
绝大多数交易业务接受最终一致性，不追求实时强一致。

## 主从复制的流程？
master主库，有数据更新，将此次更新的事件类型写入到主库的binlog文件中 主库会创建log dump 线程通知slave有数据更新
slave，向master节点的log dump线程请求一份指定binlog文件位置的副本，并将请求回来的binlog存到本地的Relay log中继日志中
slave 再开启一个SQL线程读取Relay log事件，并在本地执行redo操作。将发生在主库的事件在本地重新执行一遍，从而保证主从数据同步
------------------------------------------------------------------------------
## 什么是主从延迟？
指一个写入SQL操作在主库执行完后，将数据完整同步到从库会有一个时间差，称之为主从延迟。计算公式：
主库生成一条写入SQL的binlog，里面会有一个时间字段，记录写入的时间戳 t1
binlog 同步到从库后，一旦开始执行，取当前时间t2  t2-t1，就是延迟时间
注意：不同服务器要保持时钟一致
------------------------------------------------------------------------------
## 主从延迟排查方法？
通过 show slave status 命令输出的Seconds_Behind_Master参数的值来判断
为零：表示主从复制良好
正值：表示主从已经出现延时，数字越大，表示从库延迟越严重

## 如果数据量太大怎么办？
mysql表的数据量一般控制在千万级别，如果再大的话，就要考虑分库分表。除了分表外，列举了面对海量数据业务的一些常见优化手段
1. 缓存加速 引入Memcache或Redis缓存
2. 读写分离 每次写数据时会同步多份到其它的存储系统（mysql从库、es、hbase、mongodb等），生成多个备份，当用户读取数据时直接从备份存储系统获取数据。
3. 垂直拆分 垂直拆分是指按照业务功能拆分，业务表分布在不同的数据库上，这样也就将数据或者说压力分担到不同的库上面 。
   比如电商系统会拆分出会员、商品、交易、类目、营销、搜索等业务库，分别归属到不用的技术团队维护。
4. 分库分表 数据库垂直拆分后，遇到单机数据库性能瓶颈，我们可以考虑分表。
   分表又可以细分为 垂直分表 和 水平分表 两种形式。
   垂直分表：数据表垂直拆分就是纵向地把一张表中的列拆分到多个表，表由“宽”变“窄”，简单来讲，就是将大表拆成多张小表
   水平分表：表结构维持不变，对数据行进行切分，将表中的某些行切分到一张表中，而另外的某些行又切分到其他的表中，也就是说拆分后数据集的并集等于拆分前的数据集。
   目前市面有很多的开源框架，大致分为两种模式：
       Proxy模式。SQL组合、数据库路由、执行结果合并等功能全部存放在一个代理服务中。
       Client模式。常见是 sharding-jdbc，业务端系统只需要引入一个jar包即可，按照规范配置路由规则。 
       jar中处理 SQL 组合、数据库路由、执行结果合并等相关功能。
   **有一种说法：数据量大，就分表；并发高，就分库**
5. 冷热数据分离 根据二八定律，系统绝大部分的性能开销花在20%的业务。数据也不例外，从数据的使用频率来看，经常被业务访问的数据称为热点数据；反之，称之为冷数据。
   比如：电商网站，一般只能查询3个月内的订单，如果你想看看3个月前的订单，需要访问历史订单页面。
6. ES助力复杂搜索  ES是基于索引结构，无法像mysql那样使用join语句。
                所以我们在构建索引时需要将主表记录及关联表打平，整合到一条记录中。
                以倒排索引作为核心技术原理，为你提供了分布式的全文搜索服务。
7. NoSQL NoSQL数据库放弃了与分布式环境相悖的 ACID 事务，提供了另一种聚合数据模型，从而具有可伸缩性的非关系数据库。
   NoSQL 数据库分为五类：
   - 1、KV 数据库，通常基于哈希表实现，性能非常好。其中Value的类型通常由应用层代码决定。常用的如Redis，value支持String、List、Map、Set、Zset等复合结构。
   - 文档型数据库，如：MongoDB、CouchDB ，这种数据库的特点是Schema Free（模式自由），数据表中的字段可以任意扩展，
                比如说电商系统中的商品有非常多的字段，并且不同品类的商品的字段也都不尽相同，使用关系型数据库就需要不断增加字段支持，而用文档型数据库就简单很多了。
   - 列式数据库，比如Hbase、Cassandra。列式数据库基于Key来映射行，再通过列名进行二级映射，同时它基于列来安排存储的拓扑结构，
               这样当仅读写大量行中某个列时，操作的数据节点、磁盘非常集中，磁盘IO、网络IO都会少很多。
               列式数据库的应用场景非常有针对性，比如博客文章标签的行数很多，但在做数据分析时往往只读取标签列，这就很适合使用列式数据库。
   - 图数据库，在社交关系、知识图谱等场景中，携带各种属性的边可以表示节点间的关系，由于节点的关系数量多，而且非常容易变化，所以关系数据库的实现成本很高，
             而图数据库既没有固定的数据模型，遍历关系的速度也非常快，很适合处理这类问题。
   - 时序数据库，如：InfluxDB，一般用来做Metrics打点。时序数据库的优势，在于处理指标数据的聚合，并且读写效率非常高。
8. NewSQL New SQL 是新一代的分布式数据库，它具备原生分布式存储系统高性能、高可靠、高可用和弹性扩容的能力，同时还兼顾了传统关系型数据库的SQL支持。
          另外，它还提供了和传统关系型数据库不相上下的、真正的事务支持，具备了支撑在线交易类业务的能力。
          常见的 New SQL 数据库有：Google 的 Cloud Spanner、阿里巴巴的OceanBase以及开源的CockroachDB，Tidb。

## 分表后ID如何保证全局唯一呢？
分库分表后，多张表共用一套全局id，原来单表主键自增方式满足不了要求。我们需要重新设计一套id生成器。特点：全局唯一、高性能、高可用、方便接入。
- UUID
- 数据库自增ID
- 数据库的号段模式，每个业务定义起始值、步长，一次拉取多个id号码
- 基于Redis，通过incr命令实现ID的原子性自增。
- 雪花算法（Snowflake）
- 市面的一些开源框架，如：百度（uid-generator），美团（Leaf）， 滴滴（Tinyid）等

## 分表后可能遇到的哪些问题？
主键自增重复；需要雪花 / Redis 全局 ID。
跨分片不能 JOIN，靠冗余、ES、同分片路由解决。
不带分片键全表扫描；分页、排序、聚合很难做。
跨分片变成分布式事务，一致性成本变高。
唯一索引跨分片失效，必须业务层兜底。
扩容迁移难、DDL 运维重；存储过程触发器作废。
并发锁、热点数据管控复杂度上升。
